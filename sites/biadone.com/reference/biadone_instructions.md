# Biadone Company Intro Page — English Website Build Instructions

> **Purpose**: Use this Markdown document as the full production brief for creating an English-language company intro page for **Biadone**.  
> The page should communicate, within 10–15 seconds, that **Biadone is a Personal Context OS that remembers fragmented context and prepares the next action before the user has to ask**.

---

## 0. Non-Negotiable Output Requirements

1. **All final website copy must be written in English.**
2. The website should feel product-led, direct, technically credible, and action-oriented.
3. Use the OpenClaw landing/docs pattern as an **internal structural reference only**:
   - direct hero statement;
   - concrete capability examples;
   - quick-start style onboarding block;
   - docs-like clarity;
   - visible product architecture;
   - trust and control details;
   - concise calls to action.
4. **Do not mention OpenClaw on the final public page.**
5. Do not imitate OpenClaw’s mascot, humor, command-line install flow, lobster references, brand language, or visual identity.
6. Do not position Biadone as a generic chatbot, AI secretary, meeting notes app, or unlimited automation tool.
7. Always position Biadone as a **Personal Context OS** and T.I.V as the first proof product.
8. Important execution, sharing, saving, scheduling, or sending should always be described as **prepared first, then confirmed by the user**.

---

## 1. OpenClaw Reference: What to Borrow, What to Avoid

### 1.1 Borrow the Page Mechanics

Use the following page mechanics as inspiration:

| OpenClaw-style mechanic | How to translate it for Biadone |
|---|---|
| A blunt, memorable hero statement | Make the category and promise instantly clear: “The Personal Context OS that keeps your next action ready.” |
| Concrete examples immediately under the hero | Show real outcomes: meeting briefs, decision recall, action queues, work resumption, prepared replies. |
| “Works from the tools you already use” framing | Say Biadone carries context across conversations, calendars, documents, decisions, and workflows. |
| Quick Start block | Replace install commands with a product onboarding flow: Capture → Review → Confirm → Done. |
| Docs-like sections | Include “What is Biadone?”, “How it works”, “Key capabilities”, “Trust & Control”. |
| Social proof / community proof | Add placeholder-ready testimonial cards, waitlist metrics, or beta quotes only if real assets exist. |
| Ecosystem and integrations | Include a restrained integrations section without overclaiming live availability. |

### 1.2 Avoid Copying These Elements

Do not use:

- mascot-driven humor;
- terminal install commands as the main conversion path;
- “AI that actually does things” or derivative wording;
- any seafood/lobster/crustacean references;
- open-source community claims unless Biadone is actually open source;
- unsupported claims about channels, apps, or integrations;
- agent autonomy claims that imply Biadone acts without user permission.

### 1.3 Desired Result

The final page should feel like:

```text
OpenClaw's directness and product clarity
+
Biadone's quiet, premium, context-first trust system
+
T.I.V's time-value promise
```

It should not feel like a clone.

## 4. Messaging Principles

### 4.1 Lead With Time Recovered, Not AI Features

Do not start with “AI summarizes meetings.”  
Start with the time users lose when context breaks.

Preferred:

```text
Stop losing time to re-finding, re-explaining, and re-starting.
```

Avoid:

```text
Our AI automatically summarizes your meetings.
```

### 4.2 Make the Outcome Concrete

Every section should answer: “What does the user no longer have to do manually?”

Examples:

- No more rebuilding the same background before every meeting.
- No more hunting for the decision behind a task.
- No more restarting a project cold.
- No more asking, “What was the next step?”

### 4.3 Use State-Reporting Voice

The product voice should feel calm and operational, not chatty.

Use:

```text
Context prepared.
Decision found.
Draft ready for review.
2 actions need confirmation.
```

Avoid:

```text
Hey, I found something cool for you!
```

### 4.4 Emphasize Permission and Control

Any memory or action claim must include user control.

Use:

```text
Biadone prepares the next step and asks before anything important is saved, sent, shared, or scheduled.
```

Avoid:

```text
Biadone handles everything for you automatically.
```

## 20. Visual Identity Direction

### 20.1 Overall Feeling

The page should feel:

- calm;
- precise;
- premium;
- trustworthy;
- operational;
- quietly intelligent;
- less like a chatbot and more like an operating layer.

### 20.2 Color Palette

Use this palette as the starting point.

| Role | Color Name | HEX | Meaning |
|---|---|---|---|
| Main | Deep Navy | `#0F172A` | Trust, privacy, focus |
| Support | Graphite | `#1F2937` | Professional calm |
| Intelligence Accent | Signal Violet | `#6E5EF8` | Context connection |
| Clarity Accent | Focus Blue | `#2F6BFF` | Immediacy and clarity |
| Completion | Done Green | `#17B26A` | Ready, complete, confirmed |
| Background | Warm White | `#F8FAFC` | Readability and restraint |

### 20.3 Typography

Use a modern, highly legible sans-serif.

Recommended styles:

- Large, confident H1.
- Tight, concise subheads.
- Product UI labels in a slightly technical mono or tabular style.
- Avoid decorative or playful type.

### 20.4 Shape Language

Use:

- cards;
- stacked panels;
- timeline threads;
- source chips;
- permission drawers;
- status pills;
- small completion signals.

Avoid:

- humanoid assistant illustrations;
- robot mascots;
- brain graphics;
- CCTV, eye, or surveillance metaphors;
- overly futuristic neon sci-fi scenes.

### 20.5 Motion Direction

Use subtle motion to show:

```text
scattered → structured → prepared → confirmed → done
```

Recommended motion:

- cards softly grouping into a Context Pack;
- a Decision Log being populated;
- an Action Queue sliding into ready state;
- a Done Signal switching from `Needs review` to `Ready`.

### 21.2 Page Behavior

- Smooth anchor scrolling from nav items.
- Sticky CTA on desktop nav.
- Compact mobile menu.
- Responsive cards that collapse to a single column on mobile.
- Product mockup should remain legible at tablet widths.
- All interactive elements should be keyboard accessible.

### 21.3 Accessibility

- Use semantic HTML sections.
- Maintain high color contrast.
- All icons need accessible labels or hidden decorative treatment.
- CTA buttons need explicit labels.
- Avoid relying on color alone for status states.

### 21.4 Performance

- Avoid heavy 3D unless optimized.
- Use SVG or CSS for diagrams where possible.
- Lazy-load below-the-fold visuals.
- Keep motion subtle and disable or reduce it for users with reduced-motion preferences.
