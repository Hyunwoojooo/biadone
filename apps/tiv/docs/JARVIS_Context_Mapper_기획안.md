# JARVIS Context Mapper 기획안

> ChatGPT 공유 링크 기반 대화 구조화·가시화 도구  
> 문서 목적: 구현 방식이 아닌 **제품 기획·범위·화면·사용자 가치·우선순위** 정리
> 개정: Sprint 4.5 Audit 결과를 반영해 Semantic Signals와 Main Board / Review Queue 정책 추가

---

## 1. 기획 요약

**JARVIS Context Mapper**는 ChatGPT 공유 링크를 입력하면, 긴 AI 대화 속에 흩어진 주제, 논점 흐름, 결정사항, 보류사항, 다음 액션, 핵심 개념을 자동으로 정리해주는 도구다.

이 제품은 챗봇이 아니다.  
사용자가 구조화된 대화 내용에 다시 질문하는 서비스도 아니다.  
핵심은 긴 AI 대화를 다시 읽지 않아도, 사용자가 자신의 사고 흐름과 의사결정 내용을 빠르게 복구하고 외부 문서로 재사용할 수 있게 만드는 것이다.

최종 MVP 방향은 다음과 같다.

> **ChatGPT 공유 링크를 입력하면, 긴 대화를 다시 읽지 않아도 주제·흐름·결정·보류·액션을 한눈에 파악할 수 있는 구조화된 문서와 보드로 변환한다.**

---

## 2. 배경

JARVIS의 최종 목표는 사용자의 맥락을 이해하고 기억하며, 필요한 순간에 적절히 도와주는 개인 AI다.

하지만 JARVIS 전체를 한 번에 구현하기에는 범위가 너무 크다. 문서 처리, 맥락 해석, 장기기억, 검색, 요약, 개인화, 자동 실행까지 모두 개발해야 하기 때문이다.

따라서 첫 단계에서는 JARVIS의 전체 기능이 아니라, 가장 작은 핵심 모듈부터 검증한다.

그 첫 번째 모듈이 **ChatGPT 공유 링크 기반 대화 구조화·가시화 도구**다.

GPT 대화에는 사용자의 문제의식, 목표, 아이디어, 의사결정 과정, 선호, 실행 계획이 고밀도로 담겨 있다. 따라서 ChatGPT 공유 링크는 JARVIS가 장기적으로 다루어야 할 개인 맥락 데이터의 초기 실험 대상으로 적합하다.

## 3. 문제 정의

ChatGPT, Claude, Gemini 같은 LLM 서비스에서 사용자는 긴 대화를 통해 아이디어를 발전시키고, 기획을 정리하고, 의사결정을 내린다.

하지만 현재의 AI 대화 UI는 기본적으로 수직형 채팅 구조다. 대화가 길어질수록 사용자는 이전 맥락을 찾기 어렵고, 무엇을 결정했는지, 무엇이 보류되었는지, 다음에 무엇을 해야 하는지 다시 파악하기 어렵다.

특히 이전 대화 내용이 궁금해서 다시 질문하면, 그 질문과 답변이 또 대화에 쌓이면서 전체 구조는 더 복잡해진다.

핵심 문제는 다음과 같다.

> **AI와 나눈 긴 대화가 구조화된 지식 자산으로 남지 않고, 다시 읽기 어려운 선형 기록으로만 쌓인다.**

## 4. 사용자 페인포인트

### 4.1 긴 대화 복귀의 어려움

사용자는 긴 AI 대화에서 이전에 어떤 논의를 했는지 다시 찾기 어렵다.

대표적인 상황은 다음과 같다.

- “이 대화에서 최종적으로 정한 방향이 뭐였지?”
- “아직 결정 안 된 게 뭐였지?”
- “다음에 하기로 한 일이 뭐였지?”
- “처음에 어떤 문제의식에서 출발했지?”
- “내가 여러 대안 중 왜 이 방향을 선택했지?”

현재는 이 질문에 답하려면 긴 대화를 다시 스크롤하며 읽어야 한다.

### 4.2 대화 구조 부재

하나의 AI 대화 안에는 다음 정보가 섞여 있다.

- 문제 정의
- 아이디어
- 대안
- 반박
- 결정사항
- 보류사항
- 다음 액션
- 사용자 페인포인트
- 제품 방향
- 비즈니스 가설
- 기술 요구사항

현재 채팅 UI는 이 요소들을 구분해서 보여주지 못한다.

### 4.3 결정과 실행 항목의 유실

AI와의 대화 중 중요한 결정이나 다음 액션이 나오더라도, 대화가 길어지면 쉽게 묻힌다.

결과적으로 사용자는 좋은 논의를 했음에도 실제 문서, 회의, 실행 계획으로 전환하는 데 다시 시간을 써야 한다.

### 4.4 대화 재사용의 어려움

AI와 나눈 대화는 좋은 원천 데이터지만, 현재는 다른 도구나 문서로 옮겨 쓰기 어렵다.

사용자는 정리된 결과를 다음 형태로 활용하고 싶어 한다.

- 기획안
- 회의록
- PRD 초안
- Notion 문서
- Markdown 문서
- PDF 리포트
- 액션 아이템 목록
- 프로젝트 정리 문서

## 5. 제품 정의

### 5.1 한 문장 정의

> **ChatGPT 공유 링크를 입력하면, 긴 AI 대화를 주제·논점 흐름·결정사항·보류사항·액션·핵심 개념으로 자동 구조화하고 시각화해주는 도구.**

### 5.2 더 짧은 정의

> **긴 AI 대화를 다시 읽지 않아도 이해하고 활용할 수 있게 바꿔주는 Conversation Structuring Tool.**

### 5.3 JARVIS 관점 정의

> **JARVIS의 장기기억 엔진을 만들기 위한 첫 번째 대화 맥락 구조화 모듈.**

## 6. 제품 원칙

### 원칙 1. 질문 기능이 아니라 구조화 기능이 핵심이다

이 제품은 사용자가 대화 내용에 다시 질문하는 도구가 아니다.  
MVP의 핵심은 긴 대화를 다시 읽지 않아도 이해할 수 있도록 구조화하는 것이다.

따라서 MVP에서는 다음을 제공하지 않는다.

- 대화 기반 Q&A
- Ask Memory
- RAG 검색창
- 챗봇 인터페이스
- “이 대화에 대해 물어보세요” 기능

### 원칙 2. Timeline이 아니라 Thought Flow를 제공한다

ChatGPT 공유 링크에서 복원한 대화는 메시지 순서 중심의 구조를 제공하지만, 제품 화면의 핵심은 시간이 아니라 논리 전개다.

따라서 시간 기반 Timeline은 제공하지 않는다.  
대신 대화의 순서와 논리 전개를 기반으로 **Thought Flow**, 즉 논점 흐름도를 제공한다.

예시:

```text
문제 제기
↓
범위 축소 필요성
↓
첫 번째 MVP 아이디어
↓
사용자 페인포인트
↓
구조화/가시화 방향
↓
JARVIS 기술 축적과 연결
↓
제품 형태 고민
```

### 원칙 3. 원문 근거를 함께 보여준다

AI가 정리한 결과는 사용자가 검증할 수 있어야 한다.

따라서 핵심 항목에는 가능한 한 원문 근거를 함께 보여준다.

예를 들어 “Timeline은 제외한다”라는 결정사항이 있다면, 해당 결정을 뒷받침하는 사용자의 원문 발화가 함께 제공되어야 한다.

### 원칙 4. 그래프보다 읽히는 구조가 먼저다

초기 사용자는 화려한 그래프보다 다음 정보를 더 필요로 한다.

- 무슨 이야기를 했는지
- 어떤 결정을 했는지
- 무엇이 보류되었는지
- 다음에 무엇을 해야 하는지
- 그 내용이 대화 어디에서 나왔는지

따라서 MVP의 중심은 그래프가 아니라 **Overview, Topic Map, Board, Source Evidence, Export**다.

### 원칙 5. 결과는 재사용 가능해야 한다

사용자가 다시 질문하지 않는다면, 제품의 최종 가치는 Export에 있다.

정리된 결과는 외부 문서, 팀 공유, 회의 자료, 기획안으로 바로 활용할 수 있어야 한다.

### 원칙 6. 의미가 다른 사용자 신호를 섞지 않는다

TIV는 단순히 주제와 결정을 추출하는 것을 넘어, 사용자의 의도, 응답 형식 선호, 산출물 내용 조건, 문제 인식, 만족도, 질문의 해결 상태와 방향 변화를 구분해 구조화한다.

내부 분석 데이터는 최소한 다음 의미 타입을 구분해야 한다.

```text
User Intent
Preference
Content Constraint
Problem Signal
Satisfaction
Open Question
Decision
Action
Change Event
Topic
Entity
```

`Preference`는 답변의 형식·길이·표현·깊이에 대한 선호이고, `Content Constraint`는 결과물에 넣거나 뺄 내용이다. `Problem Signal`은 사용자가 겪는 문제와 불편이며, `Decision`과 `Action`은 각각 방향의 확정과 실제 수행 요청을 의미한다.

## 7. 타깃 사용자

### 7.1 초기 타깃

초기 타깃은 **AI와 긴 대화를 통해 사고·기획·문서화를 많이 하는 사용자**다.

대표 사용자:

- 창업자
- PM / PO
- 서비스 기획자
- 전략 기획자
- 연구자 / 학생
- AI를 활용해 문서를 자주 만드는 지식노동자

### 7.2 가장 먼저 집중할 사용자

초기에는 **창업자와 PM**에 집중하는 것이 적합하다.

이들은 AI와 긴 기획 대화를 자주 하고, 대화 안에 의사결정과 실행 항목이 많이 포함되며, 정리된 결과를 바로 팀 공유나 문서화에 활용할 수 있다.

초기 포지셔닝은 다음과 같다.

> **AI와 나눈 긴 기획 대화를, 팀에서 바로 쓸 수 있는 구조화 문서와 보드로 바꿔주는 도구.**

## 8. 핵심 사용 시나리오

### 시나리오 1. 창업자가 제품 아이디어를 정리하는 경우

창업자가 ChatGPT와 신규 제품 아이디어를 길게 논의했다.

대화가 길어지면서 다음 내용을 다시 찾기 어려워졌다.

- 문제 정의
- MVP 방향
- 핵심 기능
- 결정사항
- 아직 정하지 않은 쟁점
- 다음 액션

사용자는 ChatGPT 공유 링크를 입력한다.  
제품은 대화를 구조화해 Overview, Topic Map, Thought Flow, Decision/Pending/Action Board, Source Evidence, Export 결과를 제공한다.

사용자는 이 결과를 기획안 또는 팀 공유 문서로 활용한다.

### 시나리오 2. PM이 기능 기획 대화를 정리하는 경우

PM이 AI와 신규 기능에 대해 긴 대화를 나눴다.

대화 안에는 사용자 문제, 기능 목표, 요구사항, 리스크, 의사결정이 섞여 있다.

제품은 이를 구분해 보여준다.

- 사용자 문제
- 기능 목표
- 핵심 요구사항
- 결정사항
- 보류사항
- 리스크
- 다음 액션

PM은 이 결과를 PRD 초안이나 회의 준비 자료로 활용한다.

### 시나리오 3. 연구자 또는 학생이 학습 대화를 정리하는 경우

연구자나 학생이 AI와 여러 개념을 논의했다.

제품은 대화를 다음 형태로 정리한다.

- 핵심 개념
- 개념 간 관계
- 논점 흐름
- 아직 불명확한 부분
- 추가로 정리할 주제
- 학습 노트 형태의 요약

## 9. 핵심 사용자 가치

이 제품이 사용자에게 제공해야 하는 가치는 다음이다.

1. 긴 AI 대화를 다시 읽지 않아도 전체 맥락을 복구할 수 있다.
2. 대화 속 주제 구조를 한눈에 볼 수 있다.
3. 무엇을 결정했고, 무엇이 아직 보류되었는지 구분할 수 있다.
4. 다음 액션을 놓치지 않을 수 있다.
5. AI가 정리한 내용의 원문 근거를 확인할 수 있다.
6. 정리된 결과를 외부 문서로 재사용할 수 있다.
7. AI 대화를 개인 지식 자산으로 전환할 수 있다.

## 10. MVP 범위

### 10.1 MVP에 포함할 기능

| 구분 | 기능 | 설명 |
|---|---|---|
| 입력 | ChatGPT 공유 링크 입력 | 공개적으로 접근 가능한 ChatGPT 공유 링크를 입력으로 사용 |
| 요약 | Overview | 대화 전체를 한 장으로 정리 |
| 구조화 | Topic Map | 대화의 주요 주제와 하위 주제를 계층적으로 표시 |
| 흐름 | Thought Flow | 시간 대신 논점 전개 순서를 표시 |
| 맥락 분석 | Semantic Signals | Intent, Preference, Content Constraint, Problem Signal, Satisfaction, Open Question, Change Event를 구분해 내부 데이터로 생성 |
| 실행 관리 | Decision Board | 결정사항을 별도로 정리 |
| 실행 관리 | Pending Board | 아직 정하지 않은 쟁점을 정리 |
| 실행 관리 | Action Board | 다음 액션을 정리 |
| 신뢰 | Source Evidence | 주요 항목의 원문 근거 표시 |
| 재사용 | Export | Markdown, JSON 등 외부 활용 가능한 결과물 제공 |

### 10.2 MVP에서 제외할 기능

| 제외 기능 | 제외 이유 |
|---|---|
| 시간 기반 Timeline | v0.1의 핵심 가치는 시간 표시가 아니라 논점 전개 복원임 |
| Ask Memory | 사용자가 구조화된 대화에 다시 질문하지 않음 |
| 대화 기반 Q&A | MVP의 핵심 가치가 아님 |
| RAG 검색 | 제품 복잡도 증가, 초기 필요성 낮음 |
| PDF 업로드 / PDF Adapter | v0.1에서는 공유 링크 기반 검증이 우선 |
| 실시간 브라우저 캡처 | 초기 검증 범위 초과 |
| 크롬 익스텐션 | 초기에는 공유 링크 입력 기반 검증이 우선 |
| 여러 대화 자동 병합 | 장기기억 단계에서 다룰 기능 |
| 자동 사용자 프로필 생성 | 초기 가치와 직접 관련 낮고 민감도 높음 |
| 복잡한 그래프 중심 UI | 초기 사용성보다 시각적 복잡도가 커질 수 있음 |
| 협업 기능 | v0.1에서는 개인 사용 중심 |

## 11. 화면 구성

### 11.1 전체 화면 구조

권장 화면 구조는 다음과 같다.

```text
좌측: 대화 목록 / 프로젝트 목록
중앙: 구조화 결과 화면
우측: 선택 항목 상세 / 원문 근거
```

중앙 화면의 주요 탭은 다음과 같다.

```text
Overview | Topic Map | Thought Flow | Board | Entity Graph | Export
```

단, MVP에서 Entity Graph는 단순한 노드/관계 목록 수준으로 시작하고, 핵심은 Overview, Topic Map, Thought Flow, Board, Source Evidence, Export에 둔다.

---

### 11.2 Overview

Overview는 대화 전체를 한 장으로 요약하는 화면이다.

목적은 사용자가 대화 전체를 빠르게 복구하게 하는 것이다.

포함 정보:

- 대화 제목
- 한 줄 요약
- 핵심 문제
- 핵심 해결 방향
- 주요 결정사항
- 주요 보류사항
- 다음 액션 요약

예시:

```text
대화 제목
JARVIS 초기 MVP 기획 논의

한 줄 요약
JARVIS 전체를 바로 개발하기보다 ChatGPT 공유 링크를 구조화/가시화하는 도구를 첫 MVP로 만들자는 논의.

핵심 문제
긴 AI 대화가 수직으로 쌓이면서 이전 맥락, 결정사항, 보류사항, 다음 액션을 다시 찾기 어렵다.

핵심 해결책
ChatGPT 공유 링크를 입력하면 대화를 주제, 논점 흐름, 결정사항, 보류사항, 액션으로 자동 구조화한다.
```

---

### 11.3 Topic Map

Topic Map은 대화 전체를 주제별 계층 구조로 보여주는 핵심 화면이다.

예시:

```text
JARVIS 초기 MVP
├─ 최종 비전
│  └─ 개인 AI 비서 JARVIS
│
├─ 현재 제약
│  ├─ 개발 범위가 큼
│  ├─ 문서처리 기술 부재
│  ├─ 맥락 해석 기술 부재
│  └─ 장기기억 기술 부재
│
├─ 첫 번째 모듈 아이디어
│  ├─ ChatGPT 공유 링크 입력
│  ├─ 대화 맥락 파악
│  ├─ 구조화
│  └─ 가시화
│
├─ 사용자 페인포인트
│  ├─ 대화가 수직으로 누적됨
│  ├─ 이전 내용 확인이 어려움
│  ├─ 다시 질문하면 대화가 더 복잡해짐
│  └─ AI가 긴 맥락을 놓침
│
└─ 제품 형태 고민
   ├─ 웹 서비스
   └─ 크롬 익스텐션
```

각 주제는 클릭했을 때 관련 요약, 관련 결정사항, 보류사항, 액션, 원문 근거를 볼 수 있어야 한다.

---

### 11.4 Thought Flow

Thought Flow는 Timeline의 대체 화면이다.

시간이 아니라 **논점의 전개 순서**를 보여준다.

예시:

```text
[1] JARVIS 전체 개발 범위가 너무 크다
        ↓
[2] 따라서 모듈 단위로 쪼개서 개발해야 한다
        ↓
[3] 현재 팀은 문서처리, 맥락 해석, 장기기억 기술이 없다
        ↓
[4] 가장 접근하기 쉬운 데이터는 ChatGPT 공유 링크다
        ↓
[5] ChatGPT 공유 링크를 구조화/가시화하면 사용자 페인포인트를 해결할 수 있다
        ↓
[6] 동시에 사용자 데이터와 맥락 이해 기술을 확보할 수 있다
        ↓
[7] 초기 제품 형태는 웹 또는 크롬 익스텐션 중 선택해야 한다
```

화면 내에서는 시간 표현을 사용하지 않는다.

사용 가능한 명칭:

- Thought Flow
- Conversation Flow
- 논점 흐름도
- 사고 전개도
- Thread Flow

추천 명칭은 **Thought Flow**다.

---

### 11.5 Decision / Pending / Action Board

Board는 대화에서 나온 실행 가능한 정보를 세 가지로 나누어 보여준다.

```text
┌──────────────┬──────────────┬──────────────┐
│ 결정사항      │ 보류사항      │ 다음 액션      │
├──────────────┼──────────────┼──────────────┤
│ MVP 방향 확정 │ PDF Adapter/익스텐션 │ 공유 링크 검증 │
│ Timeline 제외│ Export 범위   │ 화면 설계      │
│ Ask 기능 제외│ Entity Graph  │ 사용자 테스트  │
└──────────────┴──────────────┴──────────────┘
```

각 카드에 포함할 정보:

- 제목
- 설명
- 분류
- 관련 주제
- 원문 근거

이 화면은 사용자가 “그래서 뭘 정했고, 뭘 안 정했고, 다음에 뭘 해야 하지?”를 가장 빠르게 확인하는 영역이다.

Board는 확정 결과와 검토 필요 결과를 구분한다.

```text
Main Board
- 사용자의 명시적 근거가 있음
- evidence가 검증됨
- confidence 0.75 이상
- 상태 충돌이 없음

Review Queue
- candidate 또는 assistant suggestion
- confidence 0.75 미만
- example-derived 가능성이 있음
- evidence 불일치 또는 다중 상태 충돌이 있음
```

Preference, Content Constraint, Problem Signal, Satisfaction, Open Question, Change Event를 모두 기본 화면에 노출할 필요는 없다. 그러나 Overview와 Board가 신뢰할 수 있는 결과를 만들려면 내부 분석 데이터와 검수 화면에서는 이 타입을 유지해야 한다.

---

### 11.6 Source Evidence

Source Evidence는 AI가 정리한 결과의 신뢰를 보강하는 화면 또는 우측 패널이다.

포함 정보:

- 선택한 항목명
- 항목 요약
- 관련 원문 발화
- 근거 유형

근거 유형 예시:

- 직접 발화: 사용자가 명시적으로 말한 내용
- 대화 기반 정리: 대화 흐름상 도출된 내용
- 추론: 여러 문장을 종합해 해석한 내용

Source Evidence는 단순 부가 기능이 아니라, AI 구조화 결과를 사용자가 신뢰하게 만드는 핵심 장치다.

---

### 11.7 Entity Graph

Entity Graph는 대화에서 등장한 핵심 개념과 관계를 보여주는 화면이다.

다만 MVP에서는 복잡한 그래프 시각화보다, 핵심 entity와 relation을 검증 가능한 데이터로 보여주는 데 집중한다.

예시:

```text
[JARVIS]
 ├─ 목표 → 개인 AI 비서
 ├─ 문제 → 개발 범위 과대
 ├─ 필요 기술 → 문서처리
 ├─ 필요 기술 → 맥락 해석
 ├─ 필요 기술 → 장기기억
 ├─ 첫 MVP → ChatGPT 공유 링크 구조화 도구
 └─ 제품 형태 후보 → 웹 서비스 / 크롬 익스텐션
```

Entity Graph의 목적은 주제 목차가 아니라 개념 간 관계를 보는 것이다.

---

### 11.8 Export

Export는 MVP에서 매우 중요하다.

사용자가 구조화된 대화 내용에 다시 질문하지 않는다면, 정리된 결과를 외부에서 재사용할 수 있어야 한다.

초기 Export 형식:

- Markdown
- JSON

후속으로 고려할 Export 형식:

- Notion 문서
- Google Docs
- PRD 템플릿
- 회의록 템플릿
- 액션 아이템 목록

Export 결과에는 최소한 다음 정보가 포함되어야 한다.

- 대화 제목
- 한 줄 요약
- 핵심 문제
- 핵심 방향
- Topic Map 요약
- Thought Flow
- 결정사항
- 보류사항
- 다음 액션
- 핵심 개념
- 원문 근거 요약

## 13. 제품 형태에 대한 기획 판단

초기 MVP는 **웹 기반 링크 입력형 서비스**가 적합하다.

이유:

- ChatGPT 공유 링크 입력만으로 가치 검증이 가능하다.
- 사용자가 실제로 구조화 결과를 필요로 하는지 빠르게 확인할 수 있다.
- 브라우저 확장 기능 없이도 초기 사용 시나리오를 만들 수 있다.
- 제품의 핵심 가치인 구조화, 가시화, Export에 집중할 수 있다.

크롬 익스텐션은 초기 필수 기능이 아니다.

크롬 익스텐션은 다음 조건이 확인된 뒤 고려한다.

- 사용자가 반복적으로 공유 링크를 입력한다.
- 공유 링크 생성 후 입력하는 과정이 불편하다는 피드백이 많다.
- ChatGPT 외 Claude, Gemini 등 다양한 대화 플랫폼을 지원할 필요가 생긴다.
- 브라우저에서 바로 가져오는 UX가 명확한 장점이 된다.

## 15. 주요 리스크와 대응 방향

### 리스크 1. 단순 요약툴처럼 보일 수 있음

대응 방향:

- “요약”보다 “구조화”를 전면에 둔다.
- Topic Map, Board, Source Evidence, Export를 핵심 차별점으로 강조한다.
- 사용자가 바로 문서화할 수 있는 결과물을 제공한다.

### 리스크 2. 사용자가 공유 링크 입력을 귀찮아할 수 있음

대응 방향:

- 초기에는 공유 링크 입력 기반으로 가치 검증에 집중한다.
- 반복 사용이 확인되면 더 쉬운 가져오기 방식을 후속으로 검토한다.

### 리스크 3. AI 정리 결과를 신뢰하기 어려울 수 있음

대응 방향:

- 주요 항목마다 원문 근거를 제공한다.
- 명시적으로 나온 내용과 추론된 내용을 구분한다.
- 사용자가 결과를 수정할 수 있게 한다.

### 리스크 4. 그래프 UI가 복잡해질 수 있음

대응 방향:

- Topic Map과 Board를 메인으로 둔다.
- Entity Graph는 단순한 노드/관계 목록으로 시작하고, 복잡한 그래프 시각화는 후순위로 둔다.
- 초기에는 읽히는 구조를 우선한다.

### 리스크 5. 사용자가 다시 질문 기능을 기대할 수 있음

대응 방향:

- 제품 포지셔닝에서 챗봇이 아니라 구조화 도구임을 명확히 한다.
- “Ask”보다 “Export”, “정리”, “보드”, “문서화”를 강조한다.

## 18. 최종 포지셔닝 문구

### 짧은 버전

> **AI와 나눈 긴 대화를, 다시 꺼내 쓸 수 있는 구조화된 문서와 지도로 바꿔주는 도구.**

### 제품 소개 버전

### JARVIS 내부 정의

> **JARVIS Context Mapper는 사용자의 AI 대화를 구조화된 맥락 데이터로 변환하는 첫 번째 기억 엔진 실험 모듈이다.**

## 19. 결론

이 기획의 핵심은 JARVIS 전체를 바로 만들지 않는 것이다.

대신 JARVIS에 필요한 가장 작은 핵심 능력부터 제품으로 검증한다.

그 능력은 다음이다.

> **비정형 대화를 읽고, 그 안의 맥락·주제·결정·보류·액션·개념을 구조화하는 능력.**

초기 데이터 소스는 ChatGPT 공유 링크다.  
시간 기반 UI가 핵심 가치가 아니므로 Timeline은 만들지 않는다.  
사용자가 다시 질문하지 않으므로 Ask/RAG도 만들지 않는다.

따라서 최종 MVP는 다음 조합으로 확정한다.

> **Share Link Input + Overview + Topic Map + Thought Flow + Decision/Pending/Action Board + Entity Graph + Source Evidence + Export**

이 범위가 현재 팀이 제로베이스에서 시작할 때 가장 현실적이고, 동시에 JARVIS의 장기기억 엔진으로 확장 가능한 첫 번째 제품 범위다.
