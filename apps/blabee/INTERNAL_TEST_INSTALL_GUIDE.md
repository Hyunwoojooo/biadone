- 대상: Blabee 개발팀과 지정된 내부 테스터
- 대상 빌드: `Blabee 0.1.0-internal`, build `21`, Apple Silicon(`arm64`) 전용

포함된 `START_HERE_KO.txt`를 설치·연결 안내로 사용한다.

## 먼저 알아둘 점

### 앱 실행형 서비스 사용 안내

이번 내부 빌드는 **앱 실행형 서비스 · 내부 테스트** 모드를 포함한다. 기본값은 꺼짐이며
사용자가 직접 켠다. build 13의 개발 Mac 설치본에서 연결·정상 종료·재실행·단일 세션
선택 왕복을 확인했지만, 새 DMG의 다른 Mac 설치나 장시간 안정성까지 통과한 것은 아니다.

1. Blabee 설정에서 기존 **macOS 자동 시작 서비스**가 등록돼 있으면 명시적으로
   **등록 해제**한다. 앱이 기존 등록을 자동으로 변경하지 않는다.
2. **앱 실행형 서비스 켜기**를 누르고 **서비스 연결됨**까지 확인한다.
3. 이후에는 Blabee 앱을 열면 서비스도 함께 시작한다. 패널의 X는 화면만 닫는다.
4. 메뉴바 우클릭 → **Blabee 종료**를 누르면 앱이 시작한 서비스도 종료된다.
5. 실패 시 설정의 진단 코드를 확인하고 **서비스 다시 시작**을 누른다. 자동으로
   무한 재시작하거나 이전 Codex 작업을 재전송하지 않는다.

로그인 시 상주하는 서비스가 아니며, 모드를 해제하려면 **앱 실행형 끄기**를 누른다.
기존 SMAppService 서명/자동 시작 오류와 다른 Mac 설치 자격은 별도 미해결 항목이다.

로컬 build 27부터 최초 서비스 시작은 Keychain 접근 확인을 위해 최대 2분 기다린다.
기존 빌드는 이 확인 도중 12초가 지나면 서비스를 종료할 수 있었다. macOS의 Blabee
접근 요청을 확인하고 **서비스 연결됨**까지 기다린다. 연결 후 응답 장애의 확인 기한은
기존 12초를 유지한다. 시작 기한을 넘겼다면 **서비스 다시 시작**으로 수동 복구한다. 서비스 메모리 증가도
관찰되어 조사 중이다. 반복 암호 요청, 지속적인 메모리 증가나 응답 지연이 있으면 테스트를
중단하고 빌드 번호·시각·증상을 전달한다. 자세한 내용은 함께 받은
[r21 릴리스 기록의 알려진 제한](INTERNAL_DMG_R21_RELEASE_KO.md#알려진-제한)을 참고한다.

#### 2026-09-11 로컬 build 27 검증

- 수정본: `build/local-service-20260911-r27/Blabee.app`. 개발 Mac의
  `/Applications/Blabee.app`에 build `27` 설치 및 실행 파일 일치를 확인했다.
- 설치된 앱이 생성한 서비스의 시작을 15초 지연시킨 후 재개했고,
  기존 12초 기한을 넘어 생존한 뒤 `서비스 연결됨`으로 전환되는 것을 확인했다.
- 서비스 관련 Swift 테스트 21개와 MCP 오류 전달 테스트 2개가 통과했다.
  공식 Codex `0.154.0`의 새 세션에서 현재 Hook 바인딩으로 `emit_decision`을
  한 번 호출하여 `accepted=true`, `BLABEE_R27_NATIVE_DELIVERY_OK`를 확인했다.
- 이 결과는 일반 Codex Plugin 연결과 앱 실행형 서비스에 대한 검증이다.
  Doctor의 별도 관리형 runtime fingerprint/버전 자격은 통과하지 않았으며,
  이번 확인에서 Pet 선택 후 Codex로 돌아오는 동작과 다른 Mac 설치는 검증하지 않았다.

### DMG 설치 절차

새 내부 DMG는 앱 설치 안내와 설치 후 설정 화면을 제공한다. 소스 코드를 내려받거나
dogfood 명령을 복사할 필요가 없다. 로컬 r21 앱에서 설치 안내와 새 build `21`·기존
build `18` 표시는 확인했지만 설치·교체 버튼은 누르지 않았다. 앱 실행은 설치 완료가
아니며, r21 설치 후 서비스·Hook·선택 반환·승인 왕복은 아직 미검증이다.
DMG와 ZIP의 검사 결과는 [r21 릴리스 기록](INTERNAL_DMG_R21_RELEASE_KO.md)을 확인한다.

가장 짧은 설치 순서는 다음과 같다.

1. DMG 안의 `Blabee.app`을 실행하고 **응용 프로그램에 설치하고 시작**을 누른다.
   기존 앱이 있으면 먼저 [업데이트 절차](#8-내부-빌드-업데이트하기)를 따른다.
2. Blabee 설정에서 사용할 프로젝트를 추가하고 **앱 실행형 서비스 켜기**를 누른다.
   기존 macOS 자동 시작 서비스가 남아 있으면 먼저 명시적으로 **등록 해제**한다.
3. 같은 설정 화면에서 **Codex 연결하기**를 누른다.
4. 새 Codex 세션을 열고 `/hooks`를 실행한다.
5. Blabee의 `SessionStart`, `UserPromptSubmit`, `Stop`, `PermissionRequest`를 직접
   검토하고 신뢰한다.

**Codex 연결하기**는 Plugin 설치까지만 처리한다. Hook 신뢰는 보안상 Blabee가
대신 선택하지 않는다. 따라서 화면에 **Plugin 설치됨 · Hook 상태 확인**이 보이면
Plugin 설치는 끝났지만 Blabee가 Hook 신뢰 완료 여부를 자동 판정하지 않는다는
뜻이다. 새 Codex 세션에서 `/hooks`를 열어 사용자가 직접 상태를 확인한다.

앱 실행이나 설정 화면 열기만으로 Codex 프로세스를 실행하거나 Plugin을 설치하지
않는다. **Codex 연결하기**는 설치를, **Codex 실행 다시 검사**는 실행·설치 상태 검사를
명시적으로 요청한다. 검사는 Plugin을 설치하지 않는다. 연결 동작은 설치 후 상태를 다시 조회한다.

Blabee는 공식 Codex 실행 파일, `codex` 명령, `~/.zshrc`, alias 또는 셸 함수를
교체하거나 수정하지 않는다. `PATH`와 기본 `/resume` 동작도 바꾸지 않는다. 일반
Codex는 설치 전과 같은 방법으로 실행한다.

## 1. 설치 전에 확인할 것

다음 내부 DMG의 기본 조건은 다음과 같다.

- macOS 13 이상
- 현재 제공 파일은 Apple Silicon(`arm64`)용
- 공식 Codex CLI는 Blabee와 별도로 설치·로그인되어 있어야 함
- 현재 소스에서 Plugin 연결을 검증한 버전은 `0.151.0`, `0.152.0`, `0.152.1`,
  `0.153.2`, `0.153.4`, `0.154.0`이다. `0.153.2` Apple Silicon 공식 배포본은 고정된 전체 파일 hash까지
  일치할 때만 허용하며, 다른 버전은 Codex를 실행하거나 바꾸지 않고 지원 필요 상태로 중단
- `0.154.0` 지원은 최신 소스로 새로 빌드한 앱부터 적용된다. Plugin 연결 사전 검사는
  통과했으며, 실제 Hook→Pet→후속 실행 왕복은 별도 확인이 필요하다. build 35부터는
  고정 서명과 현재 호출 관계가 검증된 요청에 Pet의 `이번만 허용`을 제공한다. 설치 앱의
  실제 승인·실행 왕복은 아직 검증 대상이며, 자격이 없으면 `Codex에서 직접 선택`을 사용한다.
- DMG와 같은 이름의 `.sha256` 파일을 함께 전달받아야 함
- 전체 설치 smoke test는 기존 Blabee 앱, 백그라운드 서비스, 개발용 dogfood,
  Blabee Plugin이 없는 깨끗한 환경에서 수행

2026-09-10 r21 내부 테스트 후보의 파일명은 다음과 같다.

```text
Blabee-0.1.0-internal-arm64-20260910-r21.dmg
Blabee-0.1.0-internal-arm64-20260910-r21.dmg.sha256
```

SHA-256은 함께 받은 `.dmg.sha256`과 [r21 릴리스 기록](INTERNAL_DMG_R21_RELEASE_KO.md)의
검사 결과를 대조한다. 이전 빌드의 checksum을 재사용하지 않는다.
앱 버전은 `0.1.0`, 내부 build number는 `21`, 아키텍처는 정확히 `arm64`다.
파일명이 다르거나 sidecar 검사에 실패하면 사용하지 않는다. r21은 ad-hoc 서명 앱을 담는
미서명·미공증 DMG이며 `public_distribution_ready = false`다. r15 등 이전 DMG는
현재 후보로 대체된 로컬 산출물이므로 새 테스터에게 배포하지 않는다.

전달 파일은 `Blabee-0.1.0-internal-arm64-20260910-r21-testers.zip`이다. 외부
`.zip.sha256`을 확인한 뒤 압축을 풀고 `TESTER_START_HERE_KO.md`를 먼저 읽는다.
ZIP에는 DMG·DMG checksum·먼저 읽기·이 설치 가이드·[r21 릴리스 기록](INTERNAL_DMG_R21_RELEASE_KO.md)·
테스트 결과 양식·`CONTENTS.sha256`의 일반 파일 7개가 하위 폴더 없이 들어간다.
`CONTENTS.sha256`은 자기 자신을 제외한 여섯 파일의 무결성 확인용이다. 이전 빌드의
PDF는 갱신하지 않았으므로 r21 안내로 전달하지 않는다. 다른 Mac 설치·선택 왕복은 아직 미검증이다.

Intel Mac 또는 조직 정책상 미공증 앱을 실행할 수 없는 Mac에서는 테스트를
진행하지 않는다. 현재 빌드는 Universal Binary, Developer ID 서명, Apple 공증을
제공하지 않는다.

기존 개발용 dogfood 또는 다른 Blabee Plugin이 설치된 Mac에서는 **Codex 연결하기**가
충돌을 알리고 중단할 수 있다. 현재 빌드가 정확히 식별할 수 있는 단일 구형 Blabee
dogfood 연결이면 사용자가 별도 확인 화면에서 **이전 연결 정리 후 새로 연결**을 선택할
수 있다. 이 동작은 화면에 표시된 구형 Blabee Plugin과 그 marketplace만 제거한 뒤 현재
앱의 Plugin을 설치한다. 일반 Codex, 다른 Plugin, 프로젝트 파일은 변경하지 않는다.

이름·경로·활성 상태가 예상 계약과 다르거나 구형 연결이 둘 이상이면 자동 마이그레이션하지
않고 중단한다. 이 경우 해당 dogfood의 `dogfood-summary.json`에 기록된 guarded cleanup
절차를 개발 담당자와 확인하거나, 별도의 테스트 Mac 또는 사용자 계정에서 진행한다.

## 2. 받은 파일이 온전한지 확인하기

ZIP과 외부 `.zip.sha256`을 같은 폴더에 두고 터미널에서 그 폴더로 이동해 확인한다.

```sh
shasum -a 256 -c Blabee-0.1.0-internal-arm64-20260910-r21-testers.zip.sha256
```

`OK`이면 압축을 풀고, 압축을 푼 폴더에서 내부 파일과 DMG를 확인한다.

```sh
shasum -a 256 -c CONTENTS.sha256
shasum -a 256 -c Blabee-0.1.0-internal-arm64-20260910-r21.dmg.sha256
```

모두 `OK`일 때만 설치한다. 실패하면 DMG를 열지 말고 배포 파일을 다시 받는다.
DMG 파일명이나 `.sha256` 내용을 임의로 고치지 않는다. checksum은 파일 손상·불일치
확인용이며 출처 보증, Developer ID 서명이나 Apple 공증을 대신하지 않는다.

## 3. Blabee 앱 설치하기

1. 검증을 통과한 전달받은 `.dmg` 파일을 연다.
2. DMG 창의 `Blabee.app`을 실행한다. **Blabee 설치가 필요합니다** 안내에서
   원본 build `21`과 설치 위치 `/Applications/Blabee.app`을 확인한다.
3. **응용 프로그램에 설치하고 시작**을 누른다. 기존 앱이 있으면 아래 업데이트 절차의
   정상 종료·백업 확인을 먼저 따른다. 실행 중인 앱 위에 강제로 복사하지 않는다.
4. 설치 완료 후 응용 프로그램의 `Blabee.app`이 열렸는지 확인한다. 설치본 열기만 실패하면
   반복 교체하지 말고 안내에 따라 설치된 앱을 연다. 자동 설치가 계속 실패하면 상태를 보고한다.
5. 아래 읽기 전용 명령으로 설치된 build가 `21`인지 확인한다.

   ```sh
   /usr/libexec/PlistBuddy -c 'Print :CFBundleVersion' \
     /Applications/Blabee.app/Contents/Info.plist
   ```

6. 설치 앱 실행을 확인한 뒤 DMG를 꺼낸다.

macOS가 앱 실행을 차단하면 출처와 조직 정책을 먼저 확인한다. 허용된 내부 테스트인 경우에만
macOS의 해당 앱 개별 열기 안내를 사용한다. 조직 정책으로 차단되거나 판단이 어려우면 중단한다.
설치 안내의 Finder 대체 경로도 기존 앱 사용 중 보호를 우회하는 용도로 사용하지 않는다.

`xattr`로 quarantine을 지우거나 `spctl` 또는 Gatekeeper를 시스템 전체에서 끄지
않는다. 회사 정책으로 실행할 수 없다면 우회하지 말고 테스트를 중단한다.

Blabee는 Dock 아이콘 대신 macOS 메뉴바 아이콘으로 실행된다. 실행 직후 Dock에
일반 앱 창이 나타나지 않아도 메뉴바에 Blabee 아이콘이 보이면 정상이다.

## 4. 권장 초기 설정 순서

메뉴바의 Blabee 아이콘을 누른 뒤 우측 상단의 **상자 아이콘**을 눌러 Blabee 설정을
연다. 프로젝트, 후속 제안 모드, 백그라운드 서비스는 이 화면에서 설정한다. 아래
순서를 권장한다. **톱니바퀴 아이콘**은 단축키 설정을 여는 버튼이다.

### 4-0. 첫 화면의 연결 요약을 읽는다

r21은 연결 요약과 다음 행동 버튼을 먼저 보여 주고, 아래에 프로젝트 목록을 배치한다.
세부 버튼은 **Codex 설치 · 진단 상세**, **서비스 관리 · 자동 시작 (선택)**,
**이전 Codex 연결 정리**를 펼치면 볼 수 있다.

| 요약 표시 | 의미와 다음 확인 |
|---|---|
| Blabee 서비스 연결 필요 | 서비스 관리에서 앱 실행형 서비스를 켠다. |
| Codex 연결 설정 필요 | Codex 연결하기로 Plugin 설치를 요청한다. |
| 사용할 프로젝트를 추가하세요 | 실제 Codex 작업 폴더를 관찰 목록에 추가한다. |
| 프로젝트 설정 적용 필요 | 추가·제거한 프로젝트가 현재 서비스와 다르다. 진행 중인 요청을 마친 뒤 재시작해 적용한다. |
| 설정 준비됨 · 동작 확인 필요 | 서비스·Plugin·프로젝트 준비를 확인했다. 현재 세션의 /hooks와 실제 카드·선택 반환은 별도로 확인한다. |
| 선택 카드 수신 확인 | 표시된 프로젝트에서 카드 수신을 확인했다. 다른 프로젝트나 Codex의 작업 완료까지 보증하지 않는다. |

요약 아래 **Blabee 서비스**, **Codex Plugin**, **관찰 프로젝트**, **실제 선택 카드**를
각각 확인한다. Plugin 설치 확인은 Hook 신뢰 확인과 다르며, 저장된 세션 목록도 현재
Hook 동작의 증거가 아니다. 같은 저장소라도 다른 worktree는 자동 등록되지 않는다.

### 4-1. 관찰할 프로젝트를 먼저 추가한다

1. **관찰할 프로젝트**에서 **폴더 추가**를 누른다.
2. Codex로 작업할 프로젝트의 최상위 폴더를 선택한다.
3. 목록에 프로젝트 이름과 절대 경로가 표시되는지 확인한다.

등록한 폴더와 그 하위 경로에서만 Blabee가 연결된다. 상위 작업 폴더 전체를
무심코 등록하지 말고 실제 테스트할 프로젝트만 선택한다.

프로젝트 설정은 실행 중 서비스에 즉시 반영되지 않는다. 서비스를 켜기 전에 프로젝트를
추가하면 첫 시작부터 적용된다. 실행 중에 추가하거나 제거했다면 앱 실행형 서비스의
**서비스 다시 시작**을 누르고 **현재 서비스에서 활성** 상태를 확인한다.

상태 문구의 의미는 다음과 같다.

- **현재 서비스에서 활성**: 현재 실행 중인 서비스가 관찰 중인 경로
- **설정됨 · 서비스 재시작 후 활성**: 저장은 됐지만 현재 서비스에는 아직 미적용
- **현재 서비스에서만 활성 · 재시작 후 비활성**: 설정에서는 제거됐지만 현재
  서비스가 재시작되기 전까지는 여전히 활성

### 4-2. 후속 제안 모드를 고른다

기본값인 **스마트**를 권장한다.

- **스마트**: 실행 작업에는 항상 제안하고, 설명·분석에는 유용한 후속 선택이
  2개 이상일 때만 제안
- **항상**: 단순 답변을 포함해 적격한 최종 응답마다 제안
- **작업만**: 파일 변경, 테스트, 조사처럼 실제 작업을 수행한 응답에만 제안

이 설정은 제안 빈도만 바꾸며 Codex의 명령 권한 승인 정책은 바꾸지 않는다. 변경한
모드는 백그라운드 서비스를 재시작한 뒤 Hook에 적용된다.

### 4-3. Codex Plugin을 연결한다

1. 연결 요약의 **Codex 연결하기**를 누르거나 **Codex 설치 · 진단 상세**를 펼쳐 연결한다.
2. 작업이 끝날 때까지 앱을 종료하지 않는다.
3. 상태가 **Plugin 설치됨 · Hook 상태 확인**으로 바뀌는지 확인한다.
4. 이미 열려 있던 Codex 작업은 안전하게 마친 뒤 정상 종료하고 새 세션을 시작한다.
5. 새 세션에서 `/hooks`를 실행한다.
6. 아래 네 Hook의 이름과 내용을 직접 확인한 뒤 신뢰한다.

- `SessionStart`
- `UserPromptSubmit`
- `Stop`
- `PermissionRequest`

정확히 식별된 구형 Blabee dogfood가 발견되면 일반 연결 버튼 대신
**이전 연결 정리 후 새로 연결**이 표시된다. 첫 클릭은 변경 대상을 설명하는 확인 단계만
열고, 두 번째 확인을 해야 실제 마이그레이션이 시작된다. 경고에 표시된 marketplace 이름이
예상한 구형 Blabee 연결인지 확인한다. 알 수 없는 이름이거나 다른 Plugin을 함께 바꾸겠다는
내용이면 진행하지 않는다.

Plugin 설치와 Hook 신뢰는 서로 다른 단계다. **Codex 연결하기**가 성공해도 Hook을
신뢰하기 전에는 Pet 카드가 나타나지 않을 수 있다. 반대로 Blabee는 `/hooks`의 신뢰
버튼을 대신 누르거나 신뢰 검사를 우회하지 않는다.

연결 과정에서 Blabee는 앱에 포함된 marketplace를 공식 Codex CLI에 등록하고
`blabee@blabee-app` Plugin을 설치한다. 셸을 경유하지 않으며, 명령이 끝난 뒤 실제
marketplace와 Plugin 상태를 다시 조회한다. 단순히 명령이 종료됐다는 이유만으로
설치 성공으로 표시하지 않는다.

실행 전에는 경로 소유권·쓰기 권한·파일 identity, OpenAI 서명과 지원 버전을
확인하고 각 명령을 시작하기 직전에 같은 파일인지 다시 검사한다. 안전하지 않거나
지원하지 않는 후보는 실행하지 않으며, 다른 안전한 공식 설치 후보가 있으면 그
후보를 확인한다.

다음 상황에서는 자동으로 정리하지 않고 중단한다.

- 정확히 한 개의 알려진 구형 local dogfood 계약에 맞지 않는 Blabee Plugin 또는
  marketplace가 발견됨
- 공식 Codex CLI를 찾지 못함
- 공식 서명 또는 지원 버전을 확인할 수 없음
- 앱이 `/Applications/Blabee.app`이 아닌 위치에서 실행됨
- 설치 후 다시 조회한 상태가 요청한 버전·경로와 일치하지 않음

이때 기존 Plugin을 임의로 지우지 말고 화면에 표시된 이유를 개발 담당자에게
전달한다.

Marketplace 등록 뒤 Plugin 설치가 끝나지 않은 경우에는 **Codex 연결 마무리 필요**가
표시된다. **연결 마무리**로 설치를 다시 시도하거나 **안전하게 정리**로 Blabee가
소유한 exact `blabee-app` Marketplace만 제거할 수 있다. 다른 Marketplace나 Plugin은
자동으로 지우지 않는다.

#### Codex 실행 다시 검사와 진단 복사

**Codex 실행 다시 검사**는 Plugin을 설치하지 않는다. `result=plugin_not_installed`이면
검사 대상 Plugin이 미설치인 상태이므로 **Codex 연결하기**를 눌러야 한다.
`error_code=none`은 검사 오류가 없다는 뜻이지 연결 완료라는 뜻이 아니다.
이미 연결 버튼을 눌렀는데도 미설치라면 클릭 직후 상태·오류·시각과 아래 새 검사 결과를
함께 기록한다. 이 로그만으로 설치를 시도했는지나 실패 원인까지 확정할 수는 없다.

1. **Codex 설치 · 진단 상세**를 펼쳐 **Codex 실행 다시 검사**를 한 번 누른다.
2. 검사 중 표시와 시작 시각·경과 시간이 표시되는지 확인한다. 처리 중에는 반복 클릭하지 않는다.
3. 완료 뒤 **마지막 실행 검사 완료**, 완료 시각·소요 시간·결과·마지막 확인 단계를 확인한다.
4. **진단 정보 복사**를 누르고 텍스트 편집기에 붙여 넣는다. 검사 결과와 일치하는지,
   사용자 홈 경로·토큰·원문 로그가 포함되지 않았는지 확인한 뒤 결과 양식에 붙인다.
5. 다시 한 번 시험한다면 앞선 검사가 끝난 뒤 누른다. 결과 문구가 같아도 시작·완료 시각은
   새 시도로 갱신돼야 하며, 이후 상태 새로고침이 마지막 검사 기록을 지워서는 안 된다.

`result=plugin_installed_hook_trust_unknown`, `error_code=none`은 오류 없이 Plugin 설치
상태까지 확인했다는 뜻이다. `hook_trust=not_verified`는 거부가 아니라 **미확인**이다.
`service_and_selection_roundtrip=not_tested_by_this_check`처럼 서비스 연결과 실제 선택
반환은 이 검사에 포함되지 않는다. `/hooks` 신뢰 확인과 5-1의 왕복을 별도로 수행한다.
검사 자체가 실패하면 결과의 `stage`, `error_code`, 시작·완료 시각을 전달한다.

### 4-4. 앱 실행형 서비스를 켠다

**서비스 관리 · 자동 시작 (선택)**을 펼친 뒤 진행한다.

1. macOS 자동 시작 서비스가 이미 등록되었거나 승인을 기다리면 먼저 **등록 해제**한다.
   등록 상태가 불명확하면 새 서비스를 시작하지 말고 진단 정보를 전달한다.
2. **앱 실행형 서비스 켜기**를 선택한다. 앞 단계에서 이미 켰다면 반복할 필요가 없다.
3. **서비스 연결됨**과 프로젝트의 **현재 서비스에서 활성** 상태를 모두 확인한다.
4. 실패 시 진단 코드를 기록하고 **서비스 다시 시작**으로 수동 재시도한다.
5. 다음 앱 실행부터는 모드가 유지되어 서비스도 함께 시작한다.

내부 테스트는 이 앱 실행형 경로를 사용한다. macOS 자동 시작 서비스는 별도 기능이며
현재 ad-hoc 서명 오류가 남아 있다. 앱 실행형 모드는 로그인 시 독립 상주하는 서비스가 아니다.

앱 실행형 **서비스 다시 시작**은 앱이 소유한 자식만 다시 시작한다. macOS 등록을
재등록하는 동작과 혼동하지 않는다. 버튼 반복이나 `launchctl`·BTM 초기화 명령을
섞지 말고, 재시도 후에도 연결되지 않으면 화면과 시각을 기록하고 테스트를 중단한다.

현재 내부 빌드는 legacy login Keychain을 사용할 수 있어 macOS가 암호를 요구할 수
있다. 바로 입력하지 말고 표시된 항목이
`com.biadone.blabee.coordinator.freshness.v1`인지 먼저 확인한다. 테스트 담당자가
예상된 요청임을 확인한 경우에만 요청 앱도 Blabee인지 확인한 뒤 Mac 로그인 암호를
입력하고 **허용**을 사용한다. **항상 허용**은 선택하지 않는다. 예상하지 못한 이름,
다른 요청 앱 또는 반복되는 암호 요청이 나오면 취소하고 화면을 기록해 개발 담당자에게
전달한다.

### 4-5. 단축키를 확인한다

다른 macOS 앱과 충돌하면 Blabee가 충돌 또는 등록 실패를 표시하므로 중복되지 않는

build 35부터 명령 권한 카드에서 실제 등록된 **⌘1 이번만 승인 · ⌘2 거절 ·
⌘3 Codex에서 직접 선택**을 사용할 수 있다. 이전 빌드의 숫자 표시는 클릭용이었다.
일반 선택 카드의 Option 단축키와 상세 미리보기 설정은 별개다.

#### 로컬 build 36: 승인 소스 디버깅 후속 수정

`build/local-approval-20260912-r36/Blabee.app`에 다음 두 수정을 포함했다.
기존 build 35 앱과 검증 기록은 별도 경로에 그대로 보존한다.

- 숫자키를 겹쳐 눌렀을 때 먼저 누른 키만 떼면, 여전히 누르고 있는 다른 키가 다음
  요청을 처리할 수 있었다. 차단 중 들어온 숫자키도 추적해 각각 실제로 떼기 전까지
  재입력으로 처리하지 않는다. Hook과 관리형 승인 양쪽에서 재현한 뒤 수정했다.
- Hook의 `/private/tmp` 작업 경로가 `/tmp`로 바뀌어 최종 승인 응답의 원본 비교에서
  탈락할 수 있었다. 화면과 응답에는 원본 CWD를 보존하고 세션 조회에는 정규화한
  별도 값을 사용한다. 최종 원본 바이트 비교와 요청·세션·턴·전달 토큰 검증은 유지한다.

수정 전 두 결함을 실패 테스트로 재현했고, 수정 후 관련 Swift 테스트 **213개**가
통과했다. 경로 검증에는 0.153.4·0.154.0 각각의 승인 프로필, `/private/tmp`, `/.`,
중복 슬래시의 원본 보존과 다른 프로젝트 경로의 거절을 포함한다. 실제 설치 앱의
물리 키 입력과 Codex 명령 실행 왕복은 별도 검증이 필요하다.

build 36의 release 빌드, deep/strict 코드 서명, 런타임 무결성 검사가 통과했다.
수정한 제품 소스 4개가 컴파일 입력에 포함됐고, 빌드 중 소스·패키징 입력과 기존
build 35 파일이 변경되지 않았음을 확인했다. 검증 결과와 로그는 같은 폴더의
`verification.json` 및 `release-build.log`, `codesign-verify.log`,
`runtime-identity.json`, `swift-tests-213.log`에 있다.

이번 작업은 설치본 생성까지다. 확인 시 `/Applications/Blabee.app`은 build 35였고,
설치된 앱 파일은 변경하지 않았다. 적용할 때 위 build 36 앱을 열어 설치창의 보호
검사를 따른다. 연결된 프로세스로 교체가 막히면 해당 작업을 저장하고 정상 종료한
뒤 다시 확인한다.

후속 테스터 ZIP 생성도 완료했다. 경로는
`build/tester-distribution-20260912-r36/Blabee-0.1.0-internal-arm64-20260912-r36-testers.zip`이며,
같은 이름의 `.zip.sha256` 파일이 함께 있다. ZIP 크기는 2,729,460바이트이고 SHA-256은
`147842677e0957474a9fd16aac1f60d44dbe2c26ae0eb124fbc4a7452f172315`다.

ZIP에는 `Blabee.app`과 짧은 설치·연결 안내 `START_HERE_KO.txt`만 포함한다. 개발 로그와

#### 로컬 build 35: Codex 승인과 Command 단축키

`build/local-approval-20260912-r35/Blabee.app`에는 다음 수정이 포함된다.

- 일반 Codex Hook의 일회성 승인에 공식 0.154.0 arm64 서명 프로필을 추가한다.
  기존 0.153.4도 지원하며, 실행 중인 실제 호출자와 정확한 서명을 다시 검사한다.
- Hook 명령의 120자·한 줄 제한을 16,384 Unicode scalar로 늘린다. 줄바꿈과 탭은
  원문 그대로 보존하고 전체 명령을 140pt 높이의 스크롤 영역에서 확인한다.
  다른 제어 문자·보이지 않는 방향 변경 문자 등은 계속 거부한다.
- Codex 하위 에이전트의 `agent_id`·`agent_type`을 검증된 선택적 메타데이터로
  받는다. 이 필드로 세션·작업·명령의 승인 범위를 바꾸지는 않는다.
- 화면에 표시된 승인 요청에만 ⌘1·2·3을 연결한다. 한 요청을 처리한 뒤 숫자 키를
  뗄 때까지 다음 요청에 반응하지 않는다. 창을 숨기거나 전달 중이면 등록을 해제한다.
  등록 충돌 시 해당 ⌘ 표시는 숨기고 클릭 안내를 표시한다.

일반 Codex 실행 방법은 그대로다. 서명 자격이 없는 요청은 1번을 비활성화하며,
이미 Hook이 시간 초과·직접 선택으로 종료되어 Codex의 승인창이 나타난 요청은
Codex에서 처리한다. `request_permissions`처럼 Codex가 PermissionRequest Hook을
호출하지 않는 별도 권한 요청과 Bash가 아닌 요청도 이번 수정 범위에 포함되지 않는다.
관리형 App Server의 지원 버전·명령 표시 제한은 별도 계약으로 유지한다.

0.154.0 소스의 [일회성 승인 분기](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/tools/approvals.rs#L496)와
[세션 승인 캐시](https://github.com/openai/codex/blob/6b9826e3aa83b1a5947db50f4332cb9c65f1b340/codex-rs/core/src/tools/sandboxing.rs#L64)를
대조했다. 검증한 실행 파일 SHA-256은
`4f85982624b3898c8991cb80c0981b2aa71070e3537046c9a95950318a95afcc`, CDHash는
`506770a222b6e1e63c332cbfe40dc399876c1d2a`다. 공식 배포 archive와 실행 파일 바이트가
일치하고 OpenAI 서명 요구식을 통과했다. 이것만으로 설치본의 실제 승인 왕복을
검증했다고 보지는 않는다.

설치 후 새 승인 요청에서 ⌘1로 한 번 실행한 다음 같은 명령을 다시 요청해 별도의
승인이 필요한지 확인한다. ⌘2 거절, ⌘3 직접 선택, 창 숨김, 길게 누름, 긴 명령의
마지막 줄까지 스크롤도 확인한다. 빌드 34의 반경 20.2pt와 기존 가로폭 수정이 포함된다.

검증 결과: 관련 Swift 테스트 **209개**, Hook 프로세스·소켓 테스트 **14개** 통과.
16,384자 명령의 끝과 ⌘1·2·3 버튼을 밝은/어두운 테스트 화면에서 확인했고,
release 빌드·deep/strict 서명·런타임 무결성 검사도 통과했다. 실제 사용자 키 입력으로
설치본에서 Codex 명령이 한 번 실행되는 왕복은 아직 확인하지 않았다.

교체 버튼이 비활성화됐다. 설치본은 **build 33**으로 유지된다. 작업 저장 후 연결된

모서리와의 일치 정도가 달라질 수 있다.
독립 검토에서도 약 20.2포인트로 확인했다. 도안의 좌우 모서리 측정값에는 약
0.3포인트의 차이가 있으므로 실제 하드웨어의 정확한 반경으로 해석하지 않는다.

렌더링, release 빌드·서명·런타임 무결성 검사를 통과했다.
설치 UI에서 33→34 교체를 시도했으나 실행 중인 Blabee 관련 프로세스 보호 검사로
중단됐으며 현재 설치본은 33으로 유지됐다. Blabee와 연결된 Codex 세션을 정상 종료한 뒤

#### 로컬 build 32: 상세보기의 가로폭 유지

`build/local-preview-width-20260911-r32/Blabee.app`은 상세 미리보기의 가로폭을
일반 선택 카드 패널과 같은 460포인트로 유지한다. 기존 build 31은 미리보기를 열 때

화면이 더 작으면 화면 안으로 제한된다. 긴 내용은 큰 글씨와 줄바꿈·세로 스크롤로 읽는다.

변경 전 회귀 테스트에서 가로폭 증가와 좌우 위치 이동을 재현했다. 수정 후 미리보기·
단축키·패널 관련 테스트 120개가 통과했다. 선택지 수 1~4개, 일반·좁은·좌표가 음수인
화면에서 가로 경계 유지와 닫은 뒤 크기 복원을 검증했고, 긴 설명의 밝은/어두운
테마 렌더링도 확인했다. 이 결과는 설치본의 실제 키 입력 검증과 구분한다.
독립 코드 리뷰에서 수정 사항은 발견되지 않았고, build 32의 release 빌드·서명·
런타임 무결성 검사를 통과했다. 패키징 후 확인한 현재 설치본은 build 31이며,
이 변경은 build 32를 설치한 뒤 적용된다. 연결된 Codex와 Blabee를 정상 종료한 뒤
위 앱을 열어 설치한다.

설치 후에는 선택 카드가 보이는 상태에서 설정한 미리보기 단축키를 눌러 다음을 확인한다.

1. 상세보기를 열어도 패널의 가로폭과 좌우 경계가 그대로다.
2. 긴 내용은 줄바꿈되며 세로로 스크롤해 마지막 완료 기준까지 읽을 수 있다.
3. `Control+1~4` 설정에서는 숫자만 놓으면 미리보기가 유지되고 Control을 놓으면 기존 카드 화면과 높이로 돌아온다.
4. 상세보기를 여는 것만으로 작업이 선택되거나 실행되지 않는다.

#### 로컬 build 31: Control+1~4로 상세 미리보기

`build/local-control-preview-20260911-r31/Blabee.app`은 **Control+1~4** 조합을 추가한다.
설치 후 톱니바퀴 → **단축키 설정 → 상세 미리보기 → ⌃ + 1~4 → 저장**을 선택한다.
Control을 누른 채 숫자로 상세 내용을 열고, Control을 놓으면 닫힌다. 숫자만 놓으면
미리보기는 유지된다. 기존 선택 단축키인 Option+1~4로 작업을 실행하는 동작은 유지한다.

기존에 저장한 미리보기 조합과 기본값은 자동 변경하지 않는다. 이 옵션을 저장하면
다음 앱 실행에도 Control+1~4가 유지된다. macOS의 데스크탑 전환 키와 겹치면
시스템 설정 → 키보드 → 키보드 단축키 → Mission Control에서 해당 조합을 해제하거나
Blabee에서 다른 조합을 선택한다. Blabee가 macOS 단축키 설정을 변경하지 않는다.

2026-09-11 개발 Mac의 `CopySymbolicHotKeys` 조회에서 Control+1~4의 시스템 바인딩은
네 개 모두 비활성 상태였다. 이 조회는 다른 앱이 처리하는 단축키까지 검사하지 않는다.
설치 때는 연결된 Codex와 기존 Blabee를 정상 종료한 뒤 새 앱을 연다.

Control 조합과 기존 미리보기·선택·업데이트 회귀 테스트 146개가 통과했고,
독립 코드 리뷰에서 추가 수정 사항은 없었다. 밝은/어두운 테마의 일반·좁은 설정
화면을 렌더링해 확인했다. 실제 키보드 입력과 다른 앱의 단축키 충돌은 설치 후 확인한다.
빌드 31의 release 빌드·서명·런타임 무결성 검사를 통과했다. 개발 Mac의 설치 UI에서
30→31 교체를 시도했으나 활성 Blabee/Codex 프로세스 보호로 중단됐고 설치본은 30으로
유지됐다. 정상 종료 후 **다시 확인 → 응용 프로그램에 설치하고 시작**으로 재시도한다.

이번 선택 역시 같은 Codex 세션의 새 턴으로 도착했다. 설치·설정 적용 전이므로
build 31의 네 상세보기와 키 해제 동작은 계속 미검증으로 남긴다. 자동 테스트와
화면 조회를 반복하거나 설치를 재시도하지 않았고, 앱·프로세스·설정을 변경하지 않았다.

남은 확인 순서:

1. 작업을 저장하고 연결된 Codex 세션과 Blabee를 정상 종료한다. MCP 보조 프로세스만 따로 종료하지 않는다.
2. 위 build 31 앱을 열어 설치하고, 설치된 앱의 버전이 31인지 확인한다.
3. **단축키 설정 → 상세 미리보기 → ⌃ + 1~4 → 저장** 후 Blabee를 다시 열어 설정 유지 여부를 확인한다.
4. 네 선택지가 표시될 때 각 `Control+1~4`로 상세 내용을 확인한다. 숫자만 놓으면 유지되고 Control을 놓으면 닫혀야 한다. 미리보기만으로 작업이 실행되면 안 된다.
5. 사용자가 실제로 진행할 작업 하나를 선택한 뒤 같은 Codex 세션에 한 번만 이어지는지 확인한다. 기존 build 30의 선택 반환 결과를 build 31의 실사용 통과로 대신하지 않는다.

#### 로컬 build 29: 선택지 상세 미리보기와 단축키 설정

설치 후보는 `build/local-preview-settings-20260911-r29/Blabee.app`이다.
build 28의 고정 Command+Shift 조합을 변경한 빌드이며, 설치본 build 27과는 별도다.
관련 Swift 테스트 120개와 코드 검토를 통과했다. 미리보기 및 설정 화면의 밝은/어두운
테마·두 폭 렌더링도 확인했다. 오프스크린 설정 화면은 기존 테스트 옵션으로 시스템
glass 합성을 제외하며, 설치본의 실제 키 입력과 패널 표시 복원은 아래 수동 확인 범위다.

선택지가 표시된 동안 기본 `Control + Option + 1·2·3·4`로 해당 선택지의 전체 제목,
할 일, 지킬 조건, 완료 기준을 크게 볼 수 있다. `Option`과 숫자를 먼저 놓아도
`Control`을 누르는 동안 유지되며, `Control`을 놓으면 닫힌다. 긴 내용은 스크롤할 수 있다.
미리보기는 선택을 실행하지 않는다. 실행은 미리보기를 닫고 기존 선택 키나 버튼으로 한다.
선택지가 사라지거나 바뀌고, 연결이 끊기거나 권한·설정 화면으로 전환되면 미리보기도 닫힌다.

톱니바퀴의 **단축키 설정 → 상세 미리보기**에서 아래 조합을 선택할 수 있다.
기존 선택 키와 함께 저장·취소·기본값 불러오기를 사용한다. 숫자는 카드 순서 1~4로 고정한다.

| 미리보기 조합 | 놓으면 닫히는 키 |
| --- | --- |
| `Control + Option + 1~4` (기본값) | Control |
| `Option + Command + 1~4` | Option |
| `Control + Command + 1~4` | Control |
| 사용 안 함 | 미리보기 단축키 해제 |

저장한 기존 선택 키는 보존한다. 선택 키와 미리보기 키가 겹치면 저장 전에 안내하고,
새 미리보기 키를 등록하지 못하면 기존 설정을 유지한다. 카드가 없을 때는 미리보기 키를
상시 점유하지 않는다. 실제로 등록되지 않은 조합은 카드의 미리보기 안내에도 표시하지 않는다.

기본 조합은 [VoiceOver 핫스폿](https://support.apple.com/guide/voiceover/vo14092/mac)과,
Control+Command의 1·2번은 [Safari 사이드바](https://support.apple.com/guide/safari/cpsh003/mac)와 겹친다.
앱마다 단축키가 다르므로 필요하면 조합을 바꾸거나 미리보기를 끈다. Blabee가 macOS 설정을
변경하지는 않는다. 개발 Mac에서 세 후보의 네 조합 모두 임시 등록에 성공했고 현재 시스템
단축키 목록에 일치 항목이 없었지만, 다른 앱의 메뉴나 이벤트 처리까지 보장하는 검사는 아니다.

수동 확인 시 네 선택지 각각의 내용, 숫자를 놓은 뒤 유지, 유지 키를 놓은 뒤 닫힘,
미리보기 중 실행되지 않음을 확인한다. 원래 패널이 닫혀 있었다면 다시 숨겨지고,
열려 있었다면 원래 크기로 돌아와야 한다. 긴 설명의 마지막 완료 기준과
권한 요청·설정 화면으로 전환했을 때 미리보기가 남지 않는지도 확인한다.
VoiceOver 읽기 순서도 실제 앱에서 확인한다. 창을 표시하지 않는 자동 테스트 환경에서는
SwiftUI 접근성 트리를 얻지 못해, 자동 검증은 입력 상태·실행 차단·크기 정책·렌더링에 한정한다.

## 5. DMG 설치본으로 확인할 항목

다음 항목이 모두 맞으면 앱 설치·설정 smoke test는 통과다.

- 앱이 실행되고 메뉴바에 Blabee 아이콘이 나타난다.
- 아이콘을 누르면 Pet 패널이 열리고 바깥을 누르면 닫힌다.
- 메뉴바 아이콘을 우클릭하면 **Blabee 종료** 메뉴가 나타나고 앱이 정상 종료된다.
- 설정 화면에서 프로젝트를 추가·제거할 수 있다.
- 연결 요약에서 Plugin·프로젝트·서비스·실제 카드 상태를 각각 확인할 수 있다.
- 프로젝트 변경 후 적용 필요 안내와 서비스 재시작 후 적용 상태를 확인한다.
- 후속 제안 모드를 저장할 수 있다.
- **Codex 연결하기** 뒤 **Plugin 설치됨 · Hook 상태 확인**이 표시된다.
- **Codex 실행 다시 검사**에 진행·완료 피드백과 시각·결과가 표시된다.
- **진단 정보 복사**를 실제로 붙여 넣어 결과 일치와 비식별화를 확인한다.
- 새 Codex 세션의 `/hooks`에서 Blabee Hook 네 개를 검토할 수 있다.
- 앱 실행형 서비스가 **서비스 연결됨**으로 표시된다.
- 서비스 재시작 뒤 프로젝트가 **현재 서비스에서 활성**로 표시된다.
- 앱을 종료하고 다시 실행해도 설정 화면이 정상적으로 열린다.

다음은 Plugin 설치 확인과 별도로 검증한다.

- Codex 답변 뒤 Pet 결정 카드가 나타나는지
- Pet 선택이 같은 Codex 세션의 다음 턴으로 전달되는지
- 여러 세션의 카드가 먼저 들어온 순서대로 표시되는지
- 지원되는 경로에서 Codex 명령 권한 카드가 올바르게 전달되는지

Plugin이 설치됐다는 사실만으로 위 제품 왕복까지 성공했다고 판단하지 않는다.

### 5-1. 실제 Codex 왕복을 확인한다

1. 등록한 프로젝트 폴더에서 새 Codex 세션을 시작한다.
2. 실제 작업 요청 하나를 완료한다.
3. Codex의 원래 최종 답변이 먼저 정상적으로 끝나는지 확인한다.
4. Blabee Pet의 다음 작업 선택지 하나를 고른다.
5. 같은 Codex 세션에 새 사용자 턴이 만들어지고 선택한 작업이 실행되는지 확인한다.

Pet에 전달 완료가 표시된 것과 Codex 작업이 실제로 성공한 것은 서로 다른 결과다.
둘 다 확인한다. 두 Codex 세션에서 카드를 만들었다면 먼저 들어온 카드부터 표시되는지도
확인한다.

명령 권한 카드는 일반 다음 작업 제안과 별개다. **1 이번만 승인 · 2 거절 ·
3 Codex에서 직접 선택**을 항상 같은 순서로 표시한다. build 35부터 일반 Codex Hook의
1번은 공식 Codex `0.153.4`·`0.154.0` arm64의 고정 서명과 현재 호출 관계가 검증된 요청에만 활성화된다.
미검증 요청은 1번이 비활성이고 이유가 표시된다. 버전 번호나 Plugin 설치만으로 승인
자격을 판단하지 않는다. 일반 `codex` 실행은 그대로다.
build 36 설치 후에는 ZIP의 `START_HERE_KO.txt`와 위 build 35·36 승인 검증 순서를 따른다.
이전 r21 설치본은 [r21 간단 안내의 명령 권한 카드](TESTER_START_HERE_KO.md#명령-권한-카드--r21-확인)를 따른다.

### 5-2. 선택 사항: 읽기 전용 Doctor 확인

설치 상태를 바꾸지 않는 정적 진단은 다음과 같이 실행할 수 있다. 프로젝트 경로는
실제 테스트 폴더의 절대 경로로 바꾼다.

```sh
/Applications/Blabee.app/Contents/MacOS/blabee-coordinator doctor \
  --app /Applications/Blabee.app \
  --plugin /Applications/Blabee.app/Contents/Resources/Plugin/blabee \
  --project "/absolute/path/to/project"
```

결과는 `통과`, `사용자 조치 필요`, `실패`로 나뉜다. 이 명령의 Plugin 검사는 앱에
포함된 payload 구조를 확인할 뿐, Plugin이 Codex에 설치·활성화됐거나 Hook이 신뢰된
사실을 증명하지 않는다. 실제 설치 상태는 `codex plugin list --json`, Hook 신뢰는
새 Codex 세션의 `/hooks`에서 따로 확인한다.

일반 Codex `0.153.2`·`0.153.4`·`0.154.0` Plugin CLI 연결은 지원하지만 관리형 App Server
runtime은 별도 allowlist다. 일반 Hook 요청의 일회성 승인은 이 managed allowlist와
독립적인 서명·live ancestry 검증이며 Doctor 성공만으로 자격을 부여하지 않는다.
Doctor의 managed runtime identity,
version 또는 code-mode 항목이 실패해도 일반 Plugin 설치 실패와 같은 뜻이 아니다.
이 상태에서 관리형 권한 승인 지원을 성공으로 기록하지 않는다.

## 6. 선택 사항: 소스 기반 dogfood 검증(개발팀용)

일반 내부 테스터는 이 절차를 수행하지 않는다. 저장소의 최신 개발 변경을 DMG 제작
전에 검증해야 하는 개발팀만 사용한다. DMG 설치 절차와 섞지 않으며 Node.js 22
이상과 Xcode/Swift toolchain이 필요하다.

### 6-1. 개발용 산출물을 준비한다

저장소 루트에서 release coordinator를 빌드한다.

```sh
swift build -c release --package-path src/coordinator-swift
```

기존 경로를 덮어쓰지 않는 새 절대 경로를 정해 dogfood를 준비한다.

```sh
npm run prepare:dogfood -- \
  --binary "$PWD/src/coordinator-swift/.build/release/blabee-coordinator" \
  --output "/private/tmp/blabee-dogfood-20260904-01"
```

출력의 `dogfood-summary.json`에서 아래 값을 확인한다.

- `codex.marketplace_add.argv`
- `codex.plugin_add.argv`
- `runtime.project_enable.argv_prefix`
- `runtime.service.argv`
- `runtime.pet.argv`

JSON에 기록된 인자를 임의로 줄이거나 다른 dogfood 산출물의 값과 섞지 않는다.

### 6-2. Plugin과 프로젝트를 연결한다

`dogfood-summary.json`에 기록된 순서대로 다음 동작을 수행한다.

1. 기존 marketplace 목록을 `codex plugin marketplace list --json`으로 확인한다.
2. `codex.marketplace_add.argv`에 기록된 명령으로 해당 marketplace를 추가한다.
3. `codex.plugin_add.argv`에 기록된 selector로 Blabee Plugin을 설치한다.
4. `runtime.project_enable.argv_prefix` 뒤에 테스트할 프로젝트의 절대 경로 하나를
   붙여 실행한다.
5. 전용 터미널에서 `runtime.service.argv`를 실행하고 종료하지 않은 채 둔다.
6. 대상 프로젝트 폴더에서 평소처럼 `codex`를 새로 실행한다.
7. Codex에서 `/hooks`를 열고 Blabee의 현재 Hook 네 개를 직접 검토한 뒤 신뢰한다.
8. `runtime.pet.argv`로 개발용 Pet을 실행한다.

Codex의 공식 Hook 문서에 따라 새로 설치하거나 내용이 바뀐 비관리 Hook은 현재
정의의 hash를 사용자가 검토하고 신뢰하기 전에는 실행되지 않는다. 테스트에서
`--dangerously-bypass-hook-trust`를 사용하지 않는다.

Blabee Plugin의 Hook은 다음 네 개다.

- `SessionStart`
- `UserPromptSubmit`
- `Stop`
- `PermissionRequest`

Plugin 설치 뒤 이미 열려 있던 Codex 세션에는 새 Plugin이 소급 적용되지 않을 수
있으므로, 해당 세션을 종료하고 새 세션을 시작해 검증한다.

공식 참고:

- [Codex Plugins](https://learn.chatgpt.com/docs/plugins)
- [Codex Hooks](https://learn.chatgpt.com/docs/hooks)

### 6-3. 전체 왕복을 확인한다

대상 Codex 세션에서 실제 작업 요청 하나를 수행한다.

1. Codex의 원래 최종 답변이 먼저 정상적으로 끝난다.
2. Blabee Pet에 2~4개의 다음 작업 선택지가 표시된다.
3. 1번을 선택하면 같은 Codex 세션에 새 사용자 턴이 생성된다.
4. 실제 작업 성공과 Pet의 전달 완료 표시를 서로 다른 증거로 확인한다.
5. 두 세션에서 요청을 만들었다면 먼저 들어온 카드부터 FIFO 순서로 표시되는지
   확인한다.

명령 권한 카드는 일반 다음 작업 제안과 별개다. 현재 소스의 일반 Hook 경로는 **1 이번만 승인 ·
2 거절 · 3 Codex에서 직접 선택**을 항상 표시한다. 공식 Codex `0.153.4`·`0.154.0` arm64의
고정 서명과 현재 Hook 호출 관계가 검증된 요청에서만 1번을 활성화한다. 미검증 요청에서는
1번과 비활성 이유가 함께 보이며, 버전 번호만으로 활성화하지 않는다. 일반 `codex` 실행
방식은 바꾸지 않는다. 세션 전체·앞으로도 허용은 제공하지 않는다.

카드의 **세션 위치**는 Hook이 제공한 세션 폴더이며 실제 명령 실행 폴더/환경의 검증값이
아니다. 위치가 중요하거나 표시만으로 판단하기 어려우면 **Codex에서 직접 선택**을 누른다.
테스터는 안전한 읽기 전용 요청에서 허용 후 실제 결과, 같은 권한 재요청의 새 결정,
별도 요청의 거절과 native 복귀를 확인한다. 기존 Codex 허용 규칙이나 sandbox 때문에
권한 요청이 발생하지 않았다면 보안 설정을 바꾸지 말고 미실행으로 기록한다.
설치 성공·Plugin 검사·전달 ACK를 실제 권한 왕복 성공으로 기록하지 않는다.
관리형 App Server 실험 경로는 별도이며 현재 공개 설치 기능이 아니다.

## 7. 문제 해결

### r15 등 구형 Blabee에서 Codex 버전이 고정되거나 셸 래퍼가 남았다

**구형 셸 연결 정리**와 **이전 Plugin 연결 정리 후 새로 연결**은 다른 기능이다.
전자는 예전 `codex()` 셸 함수의 생성 파일, 후자는 Plugin·marketplace만 대상으로 한다.
신규 설치자는 구형 연결 정리를 할 필요가 없다.

1. Blabee 설정에서 **구형 연결 검사**를 누른다. 설정 화면을 열기만 해서는 정리하지 않는다.
2. 정확히 식별된 원본 v4 래퍼에 한해 **정리 내용 확인**으로 대상을 검토한다.
3. 예상한 Blabee 래퍼일 때만 **백업 후 비활성화**를 선택한다. 원본은 고유 이름으로
   보존하며 `.zshrc`, 공식 Codex, 대화 기록, Plugin, 구형 runtime 디렉터리는 쓰거나 삭제하지 않는다.
4. 성공 후 같은 셸 설정을 사용하는 **새 대화형 터미널**에서 아래 두 명령을 확인한다.

   ```sh
   type -a codex
   codex --version
   ```

이미 열린 터미널의 함수는 그대로 남을 수 있다. 기존 Codex 세션을 강제 종료하거나
실행 중인 터미널에 래퍼 파일을 다시 source하지 않는다.

**수동 수정된 래퍼는 자동 정리 거부가 정상이다.** 특히 r15에서 경로를 `.local/bin/codex`로
직접 고친 파일은 원본과 다르므로 자동 복구를 보장하지 않는다. 구버전 v1~v3, 추가 참조,
불명확한 ZDOTDIR/시작 파일, 권한·동시 변경 문제도 자동 정리를 중단한다.
이때 상태·이유·현재 터미널의 제한된 진단만 개발 담당자에게 전달한다. 전체 셸 설정을 보내거나
구형 바이너리를 삭제·symlink 교체하거나 `.zshrc`를 일괄 수정하는 우회는 하지 않는다.

### 메뉴바 아이콘이 보이지 않는다

- 응용 프로그램 폴더의 `Blabee.app`을 다시 연다.
- Activity Monitor에서 Blabee가 실행 중인지 확인한다.
- 그래도 나타나지 않으면 macOS 버전, Mac 종류, 설치 위치와 함께 화면을 기록한다.

### 서비스가 사용자 승인 필요에서 바뀌지 않는다

- **사용자 승인 필요**는 macOS 자동 시작 등록의 상태다. 내부 앱 실행형 모드와 다르다.
- 기존 등록을 명시적으로 해제한 뒤 **앱 실행형 서비스 켜기**를 사용한다.
- 등록 해제가 확인되지 않으면 반복 조작하지 말고 상태 화면을 전달한다.

### 첫 실행이 연결 시간 초과로 표시된다

- 예상된 Blabee Keychain 요청인지 먼저 확인한다. 암호 요청을 무조건 승인하지 않는다.
- 로컬 build 27부터 최초 시작은 최대 2분 기다린다. 확인 중 12초 만에 종료되던 구형
  빌드라면 수정된 앱으로 교체한다. 연결 후 장애 확인은 계속 12초 안에 이루어진다.
- 시작 기한을 넘으면 서비스가 정리될 수 있으므로, 실패 상태와 시각을 기록한 뒤
  **서비스 다시 시작**으로 재시도한다. 승인만으로 종료된 자식이 살아나는 것은 아니다.
- 반복 실패나 암호 요청은 개발 담당자에게 전달한다. 보안 검사·시간 상한을 끄지 않는다.

### 프로젝트가 ‘설정됨 · 서비스 재시작 후 활성’로 보인다

설정 파일에는 저장됐지만 현재 서비스가 이전 설정으로 실행 중이라는 뜻이다.
앱 실행형 서비스의 **서비스 다시 시작**을 누르고 실제 활성 상태를 확인한다.

### Codex 답변 뒤 카드가 나타나지 않는다

- Blabee 설정에서 Codex 상태가 **Plugin 설치됨 · Hook 상태 확인**인지 확인한다.
- 설치되지 않았다면 **Codex 연결하기**를 누른다.
- 새 Codex 세션에서 `/hooks`를 열어 네 Hook의 신뢰 상태를 확인한다.
- 대상 프로젝트가 현재 서비스에서 활성인지 확인한다.
- Plugin 연결 전에 열어 둔 세션이라면 종료하고 새 Codex 세션에서 다시 확인한다.

### 서비스는 연결됐지만 `Transport closed`로 카드 전송이 실패한다

이 오류는 현재 Codex가 사용하는 MCP 통신 연결이 닫혔다는 뜻이다. Blabee 앱의
**서비스 연결됨**은 앱과 서비스 사이의 상태이므로, 기존 Codex의 MCP 연결까지
정상이라는 증거는 아니다. Hook도 요청마다 별도로 실행되어 MCP가 끊겨도 동작할 수 있다.

2026-09-11 개발 Mac에서는 build 27 교체 중 기존 MCP 보조 프로세스를 종료한 뒤
부모 Codex를 계속 실행한 것이 원인이었다. 같은 Codex에서 전송은 반복 실패했지만,
서비스 진단의 연결·재시도·프로젝트 활성 상태는 정상이었다. build 27·29 및 Plugin
launcher로 새로 시작한 MCP 연결의 초기화·ping·도구 목록 요청 15개도 모두 성공했다.
기존 MCP 오류 회귀 테스트 2개를 통과했고, build 27·29 각각에서 존재하지 않는 서비스
소켓에 대한 오류 응답 이후에도 ping·도구 목록이 정상 응답하고 프로세스가 유지됨을 확인했다.
이 사례를 모든 `Transport closed` 오류의 원인으로 일반화하지 않는다.

1. 현재 대화의 세션 ID를 확인하고 진행 중인 작업을 마친 뒤 해당 Codex를 정상 종료한다.
2. Blabee를 실행하고 **서비스 연결됨**을 확인한다.
3. 같은 프로젝트 폴더에서 `codex resume <기존 세션 ID>`로 대화를 이어 연다.
   여기서 `<기존 세션 ID>`는 실제 ID로 바꾼다. 재개 명령은 대화를 이어 쓰며 MCP 연결은
   새 Codex 프로세스에서 다시 시작한다. 기존 Codex가 실행 중인 상태에서 중복 재개하지 않는다.
4. 재개된 턴의 새 Hook 식별자로 제안 전송과 실제 카드 표시를 확인한다. 이전 전송을
   재실행하거나 이전 Hook 식별자를 재사용하지 않는다.

Blabee의 서비스만 다시 시작하거나 앱을 다시 설치하는 것으로 이미 닫힌 Codex의
MCP 연결이 복구됐다고 판단하지 않는다. 업데이트할 때는 연결된 Codex를 정상 종료한다.
설치 검사를 통과시키려고 MCP 보조 프로세스만 따로 강제 종료하지 않는다.

### Codex 연결하기가 실패한다

- 공식 Codex CLI가 별도로 설치되어 있고 터미널에서 `codex --version`이 동작하는지
  확인한다.
- r21 설치 안내를 완료하고 `/Applications/Blabee.app`에서 설정 중인지 확인한다.
  DMG 안에서 연 설치 안내는 Codex 연결 화면이 아니다.
- 알려진 단일 구형 dogfood 안내라면 **이전 연결 정리 후 새로 연결**의 변경 대상을 먼저
  확인한다. 그 밖의 충돌은 기존 dogfood나 다른 Blabee Plugin을 자동 삭제하지 않는다.
- 같은 버튼을 반복해서 누르지 말고 표시된 상태와 오류 문구를 기록한다.

Blabee는 설치 실패를 해결하기 위해 `~/.codex`, `.zshrc`, `PATH` 또는 공식 Codex
실행 파일을 직접 고치지 않는다.

### Codex 자체가 실행되지 않거나 `/resume`이 달라졌다

Blabee 때문에 일반 `codex`, `codex resume` 또는 공식 Codex 파일을 교체해서는 안
된다. 셸 alias, `.zshrc` 수정, 별도 `codex-with-blabee` 강제 실행을 해결책으로
추가하지 말고 테스트를 중단해 재현 명령과 오류를 전달한다.

## 8. 내부 빌드 업데이트하기

### 로컬 build 30: GitHub 업데이트 확인과 상세 미리보기

설치본은 `build/local-app-update-20260911-r30/Blabee.app`이다. build 29의 상세
미리보기·단축키 설정과 메뉴바 우클릭·설정창의 **업데이트 확인**을 함께 포함한다.

1. 작업을 마치고 Blabee에 연결된 Codex를 정상 종료한다. 메뉴바 우클릭 →
   **Blabee 종료**로 기존 앱도 종료한다.
2. 위 build 30 앱을 열고 **응용 프로그램에 설치하고 시작**을 누른다.
   기존 앱과 새 앱의 버전·백업 안내를 확인하고 교체한다.
3. 설치된 앱에서 **현재 버전 0.1.0 (빌드 30)**과 **서비스 연결됨**을 확인한 뒤
   Codex를 다시 열어 기존 대화를 이어간다.
4. 메뉴바 아이콘 우클릭 → **업데이트 확인…** 또는 설정의 **앱 업데이트**에서
   조회한다. 로컬 빌드 폴더는 검색하지 않는다. 아직 GitHub 릴리스가 없다면
   **등록된 배포 버전이 없습니다**가 정상이다.

이 기능은 배포 버전 조회와 릴리스 페이지 열기를 제공한다. 자동 다운로드·설치는
포함하지 않는다. 배포 태그·버전 규칙은 [앱 업데이트 확인 안내](APP_UPDATES.md)를 참고한다.
MCP 보조 프로세스만 종료한 채 기존 Codex를 계속 사용하지 않는다.

### 로컬 build 25: 구형 앱의 사용 상태를 확인하지 못하는 경우

Codex `0.154.0`을 지원하는 로컬 build `25`는 일부 프로세스의 실행 파일 경로만
확인되지 않아 구형 앱 교체가 중단된 경우 **종료 확인 후 교체**를 제공한다.
다른 앱의 업데이트 뒤 실행 파일이 제거된 프로세스가 남아 있을 때도 이 오류가
발생할 수 있다. 이 확인은 해당 교체 한 번에만 적용된다.

1. 작업을 저장하고 Blabee에 연결된 Codex 세션을 정상 종료한다. 메뉴바의 Blabee
   아이콘을 우클릭해 **Blabee 종료**를 선택한다. 패널의 X는 앱 종료가 아니다.
2. 새 build `25`의 `Blabee.app`을 열고 **응용 프로그램에 설치하고 시작**을 누른다.
3. 일부 실행 파일을 확인하지 못했다는 안내가 나오면 **종료 확인 후 교체**를 누른다.
   앱을 다시 검사한 뒤 표시하는 원본·설치본 버전과 백업 안내를 확인한다.
4. 종료 여부를 자동 확인하지 못했다는 설명을 읽고 **종료했으며, 백업하고 교체**를
   선택한다. 종료하지 않은 작업이 남아 있으면 연결 중단이나 오류가 생길 수 있다.
5. 설치 후 `/Applications/Blabee.app/Contents/Info.plist`의 `CFBundleVersion`이
   `25`인지 확인한다. 기존 앱은 별도 백업에 보존되며, 설치본 열기만 실패하면
   **설치된 Blabee 다시 열기**로 재시도한다.

실제 실행 중인 설치본이 감지되거나, 프로세스 목록·상태 조회, 실행 잠금, 앱 무결성
검사가 실패하면 이 경로도 중단된다. 재부팅은 필수 설치 단계가 아니다.
이 수동 확인 경로는 종료 상태를 검증했다는 뜻이 아니며, 일반 설치는 계속 완전한
활동 확인을 요구한다. 아래 DMG build `21` 안내와 산출물 번호를 혼동하지 않는다.

### DMG build 21 업데이트 절차

현재 자동 다운로드 업데이트는 없다. 새 DMG를 받은 뒤 r21 설치 안내에서 교체한다.
기존 r18·r19 사용자도 이 업데이트 경로를 시험한다. 깨끗한 Mac의 최초 설치와 구분한다.

1. 새 DMG와 `.sha256`을 먼저 검증한다.
2. **구버전 Blabee.app이 아직 설치된 상태에서** macOS 자동 시작 등록이 남아 있으면
   명시적으로 등록 해제하고 `등록되지 않음`을 확인한다. 앱 실행형 모드만 사용 중이면
   등록 해제할 항목은 없으며, 다음 단계의 앱 종료로 소유 서비스도 종료한다.
3. Blabee에 연결된 Codex 작업을 안전하게 마친 뒤 해당 Codex를 정상 종료한다.
   이어 메뉴바 아이콘을 우클릭해 **Blabee 종료**를 선택한다. 패널의 X는 창만 닫으며,
   Blabee 종료만으로 Codex에 붙은 MCP 프로세스까지 종료되지는 않는다.
4. 아래 명령으로 기존 앱의 `CFBundleVersion`을 확인한다. DMG 앱의 설치 안내에서도
   원본 build `21`과 기존 build를 대조한다. 같은/더 최신 앱이면 설치된 앱 열기를 사용하며,
   예상과 다르면 교체하지 않고 개발 담당자에게 알린다.

   ```sh
   /usr/libexec/PlistBuddy -c 'Print :CFBundleVersion' \
     /Applications/Blabee.app/Contents/Info.plist
   ```

5. 새 DMG의 `Blabee.app`에서 **응용 프로그램에 설치하고 시작**을 누른다.
   대상과 백업 안내를 확인한 뒤 **백업하고 교체**를 선택한다. 기존 실행 파일만 덮어쓰지 않는다.
   **관련 프로세스가 실행 중**이면 정상 종료 여부를 확인한 뒤 **다시 확인**한다.
   계속 차단되거나 사용 상태를 확인할 수 없으면 화면을 보고하고 멈춘다. 프로세스 강제 종료,
   보호 검사 우회, 실행 중 앱 덮어쓰기는 하지 않는다.
6. 새 설치본이 실행되면 같은 명령으로 설치된 build number가 `21`인지 확인한다.
7. 프로젝트와 후속 제안 모드를 확인한다.
8. Codex 연결 상태를 새로고침하고, 앱이 Plugin 업데이트를 안내하면 설정 화면의
   연결 동작으로 새 내장 버전을 설치한다.
9. 새 Codex 세션의 `/hooks`에서 변경된 Hook을 다시 검토한다.
10. 이전에 앱 실행형 모드를 켰다면 자동 연결을 기다린다. 꺼져 있으면 직접 켠다.
    **서비스 연결됨**과 프로젝트의 **현재 서비스에서 활성**을 모두 확인한다.

앱 실행형 연결 실패 시 진단 정보를 남기고 **서비스 다시 시작**을 수동으로 사용한다.
이 모드가 기존 macOS 자동 시작 서명 문제를 고치는 것은 아니다. 공개 업데이트 경험을
제공하려면 안정적인 Developer ID 서명과 공증된 빌드, 지원 macOS별 자격 시험이 필요하다.

서비스 등록을 해제하지 않은 채 ad-hoc 앱을 교체하면 macOS가 이전 코드에 저장한
launch constraint와 새 앱을 다르게 판단해 `OS_REASON_CODESIGNING` 또는
`needs LWCR update`로 실행을 거부할 수 있다. build number 증가는 필요한 구분자이지만
이 등록 경계를 대신하지 않는다. 정상 업데이트에 `launchctl`이나 BTM 전체 초기화
명령을 사용하지 않는다.

현재 업데이트·다운그레이드와 설정 보존은 깨끗한 Mac에서 최종 자격을 통과하지
않았다. 이상이 있으면 이전 앱을 임의로 섞어 복구하지 말고 빌드 버전과 증상을
기록한다. 개발용 dogfood Plugin은 해당 산출물의 `dogfood-summary.json`에 기록된
guarded cleanup 절차를 먼저 완료한 뒤 새 산출물을 설치한다.

2026-09-08 build 13 설치본에서는 앱 실행형 연결·정상 종료·재실행과 공식 Codex 0.153.4의
실제 선택 왕복을 확인했다. 기록은 `APP_OWNED_SERVICE_PLAN_KO.md`에 있다. 새 DMG는
별도의 패키징 산출물이므로 build 13 실사용 결과를 새 DMG 설치 성공으로 간주하지 않는다.

깨끗한 Mac 최초 설치, 다른 macOS 버전, 새 DMG 설치 후 Hook/Pet 왕복, 관리형 Codex
승인 및 장시간 메모리 안정성은 별도 확인 대상이다.

## 9. 제거하기

1. Blabee 설정의 Codex 연결 영역에서 **연결 해제**를 선택한다.
2. 연결 해제 뒤 Blabee Plugin과 `blabee-app` marketplace가 더 이상 등록되지 않은
   상태인지 확인한다.
3. **앱 실행형 끄기**를 선택한다. macOS 자동 시작 등록도 남아 있다면 **등록 해제**한다.
4. 등록한 프로젝트를 목록에서 제거한다.
5. 패널의 X는 창만 닫으므로, 메뉴바 아이콘 우클릭 → **Blabee 종료**를 선택한다.
6. 응용 프로그램 폴더의 `Blabee.app`을 휴지통으로 이동한다.

연결 해제는 Blabee가 정확히 설치한 항목만 대상으로 한다. 다른 marketplace의
Blabee Plugin이나 개발용 dogfood가 발견되면 자동으로 삭제하지 않는다.

앱을 지워도 `~/Library/Application Support/Blabee`의 설정, DB, key 파일 또는
Keychain 항목이 남을 수 있다. 현재 내부 빌드는 완전한 제거 도구를 제공하지 않는다.
이 파일들을 Finder나 터미널에서 임의로 삭제하면 freshness 보호 때문에 남은 상태가
복구 불가능해질 수 있으므로, 완전 정리가 필요하면 개발 담당자와 함께 정확한 상태를
확인한 뒤 진행한다.

개발용 dogfood는 앱 삭제 대신 해당 `dogfood-summary.json`의 cleanup 순서와
guarded rotation 명령을 사용한다. 실행 중 Codex, Pet 또는 service가 있으면 정리를
강제로 진행하지 않는다.

## 10. 테스트 결과를 전달할 때

다음 항목을 함께 보낸다.

- 사용한 DMG의 실제 파일명
- 함께 받은 `.sha256` 파일의 검사 성공 여부와 확인된 SHA-256 값
- Mac 모델/아키텍처와 macOS 버전
- Codex 연동을 시험했다면 `codex --version`
- 앱 설치 위치
- 설정 화면의 Codex Plugin 상태 문구
- 연결 요약의 제목·다음 행동과 Plugin·프로젝트·서비스·실제 카드의 개별 상태
- **진단 정보 복사**로 얻은 실행 검사 결과와 재검사 진행·완료 표시 확인 여부
- 앱 실행형 서비스 상태와 macOS 자동 시작 서비스 상태를 각각 기록
- 신규 설치/이전 빌드 업데이트 여부, 구형 래퍼 검사·확인·비활성화 중 실제 수행한 단계
- `/hooks`에서 확인한 `SessionStart`, `UserPromptSubmit`, `Stop`,
  `PermissionRequest` 각각의 상태
- 메뉴바 실행, 프로젝트 활성화, Plugin 설치, Hook 확인, Pet 카드 표시,
  같은 세션의 다음 턴 전달을 각각 `통과`, `실패`, `실행하지 않음`으로 구분한 결과
- 두 세션을 시험했다면 카드가 들어온 순서와 실제 표시 순서
- 명령 권한 카드를 시험했다면 세 선택지·고정 번호·1번 활성 여부·비활성 이유와
  실제 승인 결과·같은 명령 재요청의 새 결정을 일반 후속 제안 왕복과 구분한 결과
- 실패한 단계, 발생 시각, 재현 순서와 화면에 표시된 마지막 오류 문구
- 필요한 경우 민감 정보가 보이지 않는 화면 캡처

비밀번호, token, API key, 전체 Keychain 내용, 전체 journal 또는 다른 프로젝트의
대화 내용은 보내지 않는다.

이번 DMG의 제작·검증 범위와 공개 배포 전 남은 사항은 함께 받은
[`INTERNAL_DMG_R21_RELEASE_KO.md`](./INTERNAL_DMG_R21_RELEASE_KO.md)를 참고한다.
