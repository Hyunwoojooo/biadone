# Blabee 스마트 후속 제안 정책

상태: 구현 기준 확정
날짜: 2026-08-30
적용 범위: Codex Plugin, Coordinator Hook 컨텍스트, macOS Pet 설정

## 1. 목적

Blabee는 코드 작업이 끝났을 때뿐 아니라, 사용자가 충분한 설명이나 분석을 받은 뒤 자연스럽게 이어갈 수 있는 다음 질문도 Pet에서 바로 선택할 수 있게 한다.

별도의 LLM API는 추가하지 않는다. 현재 답변과 맥락을 가장 잘 아는 Codex가 기존 `blabee.emit_decision` 도구로 2~4개의 구조화된 후속 항목을 만든다. Blabee는 이를 검증하고 표시하며, 사용자가 고른 항목을 같은 Codex 세션의 새 사용자 턴으로 전달한다.

## 2. 제안 모드

| 모드 | 표시 기준 | 용도 |
|---|---|---|
| `smart` | 실행형 작업은 항상 제안한다. 설명·분석·일반 Q&A는 서로 다른 유용한 후속 항목이 2개 이상일 때만 제안한다. | 제품 기본값 |
| `always` | 메인 에이전트의 모든 적격 최종 응답에서 2~4개의 유용한 후속 항목을 제안한다. | 제안을 자주 받고 싶은 사용자 |
| `action_only` | 완료·부분 완료·실패·차단된 실행형 작업에서만 제안한다. | 기존 동작을 원하는 사용자 |

모든 모드에서 다음 응답은 제외한다.

- Codex 네이티브 권한 승인과 네이티브 질문
- 하위 에이전트의 내부 보고와 사용자에게 전달되지 않는 중간 상태
- 현재 Hook의 정확한 프로젝트·세션·턴·프롬프트 바인딩이 없는 응답
- 사용자가 도구 호출이나 부수 효과를 명시적으로 금지한 응답
- 정확한 출력 하나, 명령의 정확히 한 번 실행 또는 추가 작업 금지를 요구한 응답

실행형 요청은 기존 필수 제출 규칙을 유지하며 2~4개의 서로 다른 실제 다음 작업을 제공한다. 설명·분석·일반 Q&A에만 “유용한 후속 항목이 2개 이상” 기준을 적용한다. `smart`는 단순 상태 확인, 짧은 확인 답변과 잡담에도 제안을 만들지 않는다. `always`는 이런 informational 응답도 원칙적으로 포함하지만, 실제 후속 항목이 2개 미만이면 내용을 꾸며내지 않고 생략한다.

## 3. 전송 계약

첫 구현에서는 frozen `Contracts/v1`을 바꾸지 않는다.

- `schema_version`은 `1.0`이다.
- `interaction_kind`는 계속 `blabee_decision`이다.
- 기존 `next_actions` 배열에 우선순위가 높은 순서로 2~4개를 넣는다.
- 설명 뒤에 제시하는 후속 질문도 선택되면 그대로 실행할 수 있는 완전한 `title`, `objective`, `constraints`, `done_when`을 가진다.
- `suggestion_kind` 같은 새 필드를 추가하지 않는다.
- 기존 exact-key 검증, packet 생성, FIFO, journal, 같은 세션의 새 턴 전달을 그대로 사용한다.

따라서 첫 구현에서는 작업 후속 제안과 설명 후속 제안을 영속 데이터나 카드 종류로 따로 구분하지 않는다. 실제 사용에서 다른 카드 표현, 만료 시간 또는 알림 정책이 필요하다는 증거가 생기면 v2 계약으로 별도 설계한다.

## 4. 정책 전달

Coordinator는 `SessionStart`와 `UserPromptSubmit`의 `additionalContext`에 서버가 만든 동일한 정책 문구와 `suggestion_mode=<mode>`를 넣는다. 두 Hook에서 서로 다른 규칙이 전달되지 않도록 컨텍스트 생성기는 한 곳에서 관리한다.

제품 서비스는 저장된 사용자 설정을 읽는다.

- 설정이 없으면 `smart`
- 올바른 값이면 해당 모드
- 알 수 없는 값이면 `action_only`로 실패 폐쇄

개발용 daemon과 기존 테스트 fixture의 기본값은 호환성을 위해 `action_only`를 유지한다.

## 5. 사용자 흐름

```text
Codex 최종 응답 준비
  → 현재 suggestion_mode 확인
  → 모드별 제안 기준 판단
  → 기준 불충족: 일반 답변만 종료
  → 기준 충족: 기존 v1 proposal 제출
  → 기존 검증·packet·FIFO로 Pet 표시
  → 사용자가 항목 선택
  → 같은 Codex session_id의 새 사용자 턴으로 전달
```

사용자가 Pet을 선택하지 않고 Codex에 새 프롬프트를 직접 입력하면, 기존 same-session supersession 규칙이 이전 제안을 닫고 새 프롬프트를 우선한다.

## 6. 예시

### `smart`에서 표시

- “로그인 오류 원인을 분석해줘”에 대한 충분한 분석 뒤 `재현 테스트 작성`, `최소 수정안 구현`, `인증 경로 보안 검토`가 모두 실제로 유용한 경우
- “이 구조를 설명해줘”에 대한 설명 뒤 `호출 흐름을 실제 코드로 추적`, `상태 모델을 예제로 설명`이 자연스러운 경우
- 코드 변경·테스트가 완료되어 다음 QA 또는 통합 작업이 있는 경우

### `smart`에서 표시하지 않음

- “지금 서비스가 실행 중이야?”에 “네, 실행 중입니다”로 끝나는 상태 확인
- “오케이” 같은 확인 답변
- 모든 모드의 공통 제외 조건에 해당하는 “UUID 하나만 출력” 같은 exact-output 요청
- 실제로 유용한 후속 항목이 하나뿐인 답변

## 7. 인수 기준

- 제품 기본 설정이 없을 때 Hook 컨텍스트에 `suggestion_mode=smart`가 들어간다.
- `smart`, `always`, `action_only` 각각에서 SessionStart와 UserPromptSubmit이 동일한 모드 정책을 전달한다.
- `action_only`는 기존 실행형 작업 동작을 보존한다.
- 설정 값이 손상되거나 알 수 없으면 `action_only`가 적용된다.
- 설명 후속 제안도 v1 exact-key 검증을 통과하며 기존 Pet FIFO와 같은 세션 새 턴 경로를 사용한다.
- Contracts/v1 schema, packet, journal event 계약에는 변경이 없다.
- 선택지를 만들기 위해 의미 없는 질문이나 중복 작업을 생성하지 않는다.

## 8. 남은 검증

- 실제 Codex에서 설명·분석·상태 확인 예제를 반복해 `smart`의 과다 표시와 누락 비율을 확인한다.
- 여러 세션에서 작업 제안과 설명 제안이 함께 도착했을 때 기존 FIFO 순서를 확인한다.
- 설정 변경 후 제품 서비스 재시작 경계와 사용자 안내가 충분한지 확인한다.
- 작업과 설명 제안에 서로 다른 카드 표현이 실제로 필요한지는 dogfood 결과로 결정한다.
