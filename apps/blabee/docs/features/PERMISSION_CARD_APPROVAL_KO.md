# 권한 카드 세 버튼 고정과 일회성 승인 검증

- 작성일: 2026-09-10 (KST)
- 이슈: `BLB-HOOK-APPROVAL-001`
- 상태: 소스 수정·자동 테스트 완료. 설치본/DMG 반영·실제 카드 왕복 검증 대기.
- 범위: 일반 Codex Hook 권한 카드. 후속 작업 제안 카드와는 별개다.

## 사용자 문제

권한 요청에서 승인 버튼이 사라지고 `1 거절 · 2 Codex에서 직접 결정`만 나타났다.
기존 모델은 `allowOnceAvailable` 값에 따라 선택지 배열을 3개 또는 2개로 만들고,
화면이 그 배열의 순번을 사용했다. 따라서 승인 가능 여부에 따라 버튼 수와
번호가 바뀌었다.

그보다 앞단의 Hook은 현재 호출자의 프로세스 관계와 실행 중 코드 서명을 검사한다.
이 검사가 실패하면 승인 자격 표시를 보내지 않는다. 화면의 두 버튼만으로 정확히 어느
검사가 실패했는지 알 수 없으며, Plugin 설치·Codex 버전 문자열만으로 통과를 추정하지 않는다.

## 변경 계약

1. `1 이번만 승인 · 2 거절 · 3 직접 선택` 순서와 번호를 유지한다.
2. 검증된 요청에서만 승인을 활성화한다. 승인할 수 없거나 전달 중인 상태는 명확히 구분한다.
3. 승인 불가 상태의 1번 버튼을 거절이나 다른 명령으로 해석하지 않는다. 버튼을 숨기지 않고
   미승인 상태와 Codex에서 직접 결정할 수 있다는 안내를 제공한다.
4. 정확한 요청·세션·턴·명령·세션 위치의 대조, 만료·중복 처리, 전달 토큰 검증을 유지한다.
5. 승인 응답은 요청 단위다. 세션 허용·명령 규칙 저장을 추가하지 않는다.

Codex 실행 방식·설치·Hook 신뢰·기존 세션·프로젝트 설정을 변경하지 않는다.
미확인 실행 파일이나 임의의 중간 프로세스를 허용 목록에 추가해 검증 실패를 우회하지 않는다.

## 검증 구분

- 모델/UI: 승인 가능·불가·전달 중에도 순서와 번호의 의미가 같아야 한다.
  기존 카드의 번호 표시는 실제 숫자 키 입력 처리와 다르다. 이번 변경에서 Codex나 다른 앱의
  숫자 키를 가로채는 전역 단축키·키보드 모니터는 추가하지 않는다.
- 실행 중 서명 조회: 실제 macOS API에서 검증된 실행 코드의 필수 정보가 읽히는지 확인한다.
  가짜 서명 데이터를 주입한 단위 테스트만으로 이 구간을 통과로 표시하지 않는다.
- 전달 계약: 같은 명령을 다시 요청하면 별도 선택이 필요하고, 이전 응답 재전송이 새 요청을
  승인하지 않아야 한다. 자격·세션·턴·명령 불일치와 만료 요청은 승인되지 않아야 한다.
- 실제 제품: 설치본의 카드 클릭 → Hook 반환 → Codex의 실제 실행을 별도로 확인한다.
  앱 빌드·소켓 ACK·Mock 응답은 실제 사용자의 승인 완료 증거가 아니다.

## 확인된 원인과 수정

`CodexHookApprovalQualification.runningSignatureEvidence`는 실행 중인 호출자의 서명을
검증한 후 `SecCodeCopySigningInformation`에 0 플래그를 전달했다. macOS의 기본 정보에는
`kSecCodeInfoTeamIdentifier`가 포함되지 않으므로, 뒤에서 요구하는 OpenAI Team ID가
`nil`로 읽혀 정상 Codex도 승인 자격을 얻지 못했다.

2026-09-10 로컬 실측에서는 공식 Codex 0.153.4 프로세스 8개가 모두 동일했다.
검증 전후 `SecCodeCheckValidity`는 성공했지만 0 플래그의 Team ID는 `nil`이었다.
동일 PID에서 `kSecCSSigningInformation`을 요청하면 `2DC432GLL2`가 반환돼 기존 조건을
충족했다. 다른 CDHash의 ChatGPT 번들 Codex 5개는 변경된 조회에서도 기존 조건을
통과하지 못했다. `/bin/sh`의 커널 경로 `/bin/bash` 및 `/bin/zsh` 중간 프로세스는
기존 Apple 서명 조건을 통과했다. 이 관찰은 해당 시점의 이 Mac에 한정한다.

변경 내용:

- 실제 reader가 `kSecCSSigningInformation`을 요청하도록 수정하고, API 호출에 전달되는
  플래그와 실패 시 결과 폐기를 테스트한다.
- 기존 실행 중 코드 객체를 유지하며 서명 검증 전후 검사, Team ID·CDHash 고정,
  사용자 ID·프로세스 시작 시각·부모 관계 재검사는 완화하지 않는다.
- 일반 Hook 카드는 승인 가능 여부와 무관하게 세 행을 표시한다. 승인 불가 사유는 1번
  행에 표시하고, 3번 `Codex에서 직접 선택`으로 원래 승인 흐름을 사용할 수 있게 안내한다.
- 관리형 카드도 같은 표시 문구를 사용하지만 기존의 별도 전달 계약은 유지한다.

## 배포와 완료 경계

이 변경은 소스·테스트·문서 수정이다. 실행 중인 Blabee/Codex를 종료하거나 앱 번들을
교체하지 않았고, Codex 설치·Hook 신뢰 설정·Plugin Hook 명령·세션 기록은 변경하지 않았다.
현재 설치본과 기존 DMG/ZIP, 앞서 생성한 build 20에는 이 수정이 들어 있지 않다.

새 빌드 적용 후 확인할 항목:

1. 일반 공식 Codex의 같은 세션에서 일회성 승인 가능 카드가 세 버튼으로 표시되는지.
2. 사용자가 1번을 선택하면 해당 요청만 실행되고, 같은 명령의 다음 요청은 다시 선택을 요구하는지.
3. 거절·직접 선택·만료 시 원래 Codex 흐름이 유지되며, 다른 세션이나 이미 끝난 요청에
   이전 응답이 적용되지 않는지.
4. 검증 불가 요청에서도 세 행과 비활성 사유가 보이는지. 버튼 표시는 실제 숫자 키 처리가
   구현됐다는 뜻이 아니며, 클릭 및 원래 Codex의 키 입력 동작은 별도로 확인한다.

## 검증 결과 (2026-09-10)

- API 실측에서 원인을 재현한 후, 수정한 `CodexHookApprovalQualification.swift`와 실제
  `HookPermissionPolicy.swift`를 임시 진입점과 함께 직접 컴파일했다. 직접 Codex 자식과
  `/bin/sh`(`/bin/bash`)를 거친 자식 모두 실제 `currentQualification()` 전체 경로에서
  자격 토큰과 `allowsOnce=true`를 반환했다. 서명·프로세스 자료를 가짜 값으로 바꾸지 않았다.
- 검증한 qualifier SHA-256:
  `a111e055385be27f825cdd7422c3dfb39fe7fa8a91f6b9e5dfd7c2aa925afda2`.
- 읽기 전용 독립 QA에서 조회 플래그·동적 서명 재검증·UI/VM/typed request 승인 차단을
  대조했고, 검토 범위의 새로운 critical/high/medium 결함은 발견하지 못했다.
- 새 화면 접근성 테스트는 보이지 않는 `NSHostingView`에서 빈 트리를 반환했다.

  없었다. 이 테스트를 통과로 처리하지 않고 제거하며, 표시 목록과 전송 정책을 별도로
  검사한다. 접근성 트리·실제 설치본의 시각/클릭 확인은 남아 있다.

- 최종 `npm run test:swift`: Swift Testing 809개와 XCTest 5개 통과.
  서명 조회 플래그/실패 폐기, 표시 목록·고정 번호, 승인 불가·전달 중·오래된 클릭 차단,
  동일 명령의 새 요청과 이전 응답 재전송 회귀를 포함한다.
