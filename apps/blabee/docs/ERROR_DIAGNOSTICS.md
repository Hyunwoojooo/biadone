# Blabee 오류 진단

## 수집 범위

2026-09-17 요청으로 추가한 선택적 앱 오류 진단이다. 설정 → 일반 → 오류 진단 → **오류 진단 보내기**는 기본 꺼짐이며, 기존 사용 통계 동의와 별개로 이 Mac에 적용한다. 로그인한 계정에서 동의한 뒤 관측한 오류만 자동 전송한다.

전송 항목은 무작위 이벤트 ID, 고정 오류 코드, 발생 시각, 앱 버전·빌드, 숫자로 된 macOS 버전이다. 사용자 ID는 검증된 로그인 토큰의 `auth.uid()`로 서버가 결정한다. 이메일은 진단에 복제하지 않고 관리자 보고서에서 필요할 때 Auth 계정과 연결한다.

로그 원문, 오류 설명 원문, 스택 추적, 대화, 코드, 명령, 경로, 프로젝트명, Codex 세션 ID, 토큰, 기기 식별자·하드웨어 정보는 보내지 않는다. 자유 형식의 문자열이나 JSON 속성 입력을 허용하지 않는다. 버전은 숫자 점 표기(각 1–6자리, 최대 4구간) 또는 `unknown`으로 제한한다.

| 코드 | 관측 대상 |
| --- | --- |
| `account_service_unavailable` | 이미 검증된 계정의 갱신/확인 중 서비스 연결 실패 |
| `account_invalid_response` | 계정 갱신/확인 응답 검증 실패 |
| `account_rate_limited` | 계정 갱신/확인 요청 제한 |
| `account_storage_unavailable` | 계정 갱신 과정의 로컬 인증 정보 저장 실패 |
| `account_refresh_failed` | 그 밖의 계정 갱신/확인 실패 |
| `coordinator_connection_failed` | 새로운 상태 조회 연결 장애의 첫 실패 |
| `coordinator_response_invalid` | 새로운 상태 조회 장애 중 응답 해석 실패 |
| `choice_submit_failed` | 선택 요청의 정상 접수 응답을 확인하지 못함 |
| `approval_submit_failed` | 기본/관리형 승인·거절 요청의 정상 응답을 확인하지 못함 |
| `suggestion_dismiss_failed` | 제안 건너뛰기의 정상 응답을 확인하지 못함 |
| `app_service_failed` | 앱 소유 서비스 시작 또는 등록 상태 확인 실패 |
| `app_service_timeout` | 서비스 준비/재연결 시간 초과 |
| `app_service_exited` | 앱 소유 서비스 자식 프로세스의 예상 밖 종료 |

응답 확인 실패가 실제 명령 실행 실패를 확정하지는 않는다. 계정 만료·로그아웃·사용자 취소는 진단에서 제외한다. 최초 로그인 전 또는 시작 중 아직 계정을 검증하지 못한 오류는 나중 계정으로 소급 연결하지 않는다. `app_service_exited`는 자식 프로세스 종료 관측이며 Blabee 앱 자체의 크래시 스택 수집을 뜻하지 않는다. 앱 전체가 갑자기 종료되는 문제의 자동 크래시 보고서는 별도 기능이다.

## 동의·계정 경계와 전송

- 요청을 시작하기 전에 동의와 검증된 계정 컨텍스트를 캡처한다. 응답 대기 중 설정을 껐다 켜거나 같은 계정으로 재로그인해도 이전 요청을 새로운 동의에 포함하지 않는다.
- 계정 갱신 중 일시적으로 전송 인증을 사용할 수 없어도 기존 계정/동의 컨텍스트의 오류는 보관할 수 있다. 검증된 같은 계정이 복구되면 전송한다.
- 명시적 로그아웃·계정 변경·수집 해제는 대기열과 컨텍스트를 폐기한다. 독립된 저장 세대를 먼저 바꾸므로 파일 삭제가 실패해도 이전 세대가 다시 전송되지 않는다. 이미 서버가 접수한 요청은 취소로 되돌릴 수 없다.
- 진단 전송은 제품 동작을 기다리게 하거나 실패시키지 않는다. 진단 전송 자체의 오류로 또 다른 진단을 만들지 않는다.
- 인증 토큰은 전송 시에만 메모리에서 사용하고 파일에 저장하지 않는다. 대기열은 Coordinator SQLite 및 사용 통계 대기열과 분리한다.
- 최대 256건·7일·128KiB 대기열과 30–300초 재시도로 제한한다. 동일 코드 60초 억제, 프로세스/계정당 시간당 50건 제한은 메모리에서 적용하며 재시작 시 초기화된다. 서버는 계정별 UTC 수신일당 200건 제한을 별도로 적용한다.
- 자동 상태 조회 오류는 같은 계정·동의 컨텍스트에서 성공적으로 복구할 때까지 첫 실패만 기록한다. 새로 동의하거나 로그인한 뒤 시작한 새 요청의 실패는 기록할 수 있지만, 동의 전 요청의 오류를 소급 기록하지 않는다.

## Supabase

`supabase/migrations/202609170002_blabee_errors.sql`은 기존 비공개 `blabee_analytics` 스키마에 오류와 전송 한도 테이블을 추가한다. RLS를 켜고 클라이언트 직접 조회/변경 권한을 부여하지 않는다. 로그인한 사용자만 `public.record_blabee_error`를 실행할 수 있으며 본문에 사용자 ID를 받지 않는다. 중복 이벤트와 한도 초과는 추가 저장 없이 `false`로 응답하여 앱의 재시도를 끝낸다. `202609170003_blabee_error_retention.sql`은 Supabase의 `pg_cron` 모듈로 일일 정리를 예약한다. 앱에 새 외부 SDK 의존성은 추가하지 않는다.

발생 시각은 서버 현재 시각 기준 과거 168시간부터 미래 5분까지 허용한다. 계정 삭제 시 해당 진단도 삭제한다. 수신 후 30일이 지난 기록을 정리하는 관리자 함수와 일일 예약 작업을 사용한다. 따라서 정상 일일 정리 사이에는 최대 약 31일의 기록이 남을 수 있다.

`supabase/error-reports.sql`은 관리자 SQL Editor용이며 오류 코드·앱 빌드·macOS별 최근 오류, 영향을 받은 계정 수, 계정별 최근 오류, 날짜별 추이를 조회한다. 수신 시각 기준 기간이며 발생 시각도 함께 표시한다. 수집 동의, 반복 억제, 오프라인 누락, 보관 기간 때문에 전체 오류 횟수나 오류율을 뜻하지 않는다. 사용 통계와 연결해 오류 후 사용 기록을 비교할 수 있지만 오류가 이탈 원인이라고 확정할 수는 없다.

SQL Editor로 적용하면 Supabase CLI 마이그레이션 이력에 자동 등록되지 않으므로 이후 CLI 관리 전 실제 스키마와 이력을 맞춘다.
