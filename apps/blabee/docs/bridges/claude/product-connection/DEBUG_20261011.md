## 재현한 결함

| 경로 | 재현과 영향 | 수정 범위 |
| --- | --- | --- |
| MCP 대기 요청 취소 | 진행 중인 RPC 하나와 대기 요청 31개를 만든 뒤 대기 요청을 취소해도 슬롯 32개가 남는다. 새 요청이 `session_v2_queue_full`로 거절된다. | 아직 전송하지 않은 요청의 취소·슬롯 반환·리스너 정리 |
| Stop Hook 출력 실패 | 실제 Writable의 write 콜백을 보류한 채 제한 시간 초과 또는 취소 후 EPIPE를 발생시키면 오류 리스너가 없어 프로세스가 종료된다. destroy 직후 늦은 성공 콜백도 실패로 처리해야 한다. | 실패한 쓰기의 늦은 오류 처리·실제 close 이벤트 시 정리 |
| Hook 입력 실패 후 취소 | 과대 입력으로 reader가 종료된 뒤 진단 출력 중 취소하면 runner가 이미 읽기를 끝낸 stdin을 오류로 destroy한다. 처리되지 않은 오류로 프로세스가 종료된다. | 두 Hook runner의 실제 입력 읽기 구간과 취소 수명 정렬 |

인증된 RPC가 이미 전송된 경우에는 응답 검증 또는 제한 시간 종료까지 슬롯을 유지한다.
출력 실패는 선택 참조를 재출력하거나 작업을 재실행하는 근거가 아니다.
기존 세션 authority·waiter generation·만료·claim·완료 binding을 유지한다.

## 검증

새 테스트 12개를 추가하고 기존 SDK 취소 테스트 5개를 강화했다.
취소 슬롯 회귀 3개는 수정 전 모두 실패했다. 신규 Hook 회귀 9개 중 7개는 기존 코드에서
처리되지 않은 stream 오류로 실패했으며, parse 실패 2개는 정상 종료하는 대조군이다.
최종 출력 회귀는 timeout/abort, destroy 직후 오류·성공 콜백, 이미 닫힌 stream의 8개 순서를
실제 Writable subprocess에서 검증한다. 독립 검토에서도 종료 경합 4개를 재확인했다.

시작 기준점은 `/private/tmp/blabee-claude-debug-20261011-ysf0lnnn/`의 실제 파일 사본이다.
같은 위치의 `queue-worker-only.patch`와 `hook-io-evidence/`에 수정 전 실패·수정 후 통과 증거를 보관한다.

Swift 선택 경로는 읽기 전용으로 검토했다. readiness, native continuation, 단일 claim,
새 카드 이후 기존 선택 완료 보고의 binding에서 확정된 결함은 발견하지 못했다.
지연된 `StopFailure`가 이전 `prompt_id`를 포함할 때 현재 관찰을 폐기하는 동작은 남은 확인 사항이다.
불확실한 관찰을 폐기하는 정책과 관련되어 실제 native 이벤트 순서 없이 변경하지 않는다.
