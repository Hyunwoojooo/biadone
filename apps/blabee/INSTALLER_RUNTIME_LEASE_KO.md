# Blabee 설치 실행 잠금 — 종료했는데 교체가 막히는 문제

- 작성일: 2026-09-10 (KST)
- 이슈: `BLB-INSTALL-001`
- 상태: 소스 수정·단위/패키징 검증 완료, 네이티브 통합·설치본 이관·다른 Mac 검증은 미완료

## 관찰과 원인

build 22 설치창의 `실행 중인 프로세스를 충분히 확인할 수 없습니다`는
**Blabee가 실행 중임을 확인했다는 뜻이 아니다.** 기존 설치 보호는 Mac의 프로세스를
열거하고, 하나라도 실행 파일 경로를 확인하지 못하면 안전상 교체를 막았다.

2026-09-10 개발 Mac의 읽기 전용 검사에서 업데이트 이전 위치에 남은 다른 앱의
보조 프로세스 6개가 `proc_pidpath`의 `ENOENT`와 대체 서명 조회 실패를 만들었다.
이들은 Blabee가 아니었다. 같은 검사 시점에는 실제 설치본 coordinator를 쓰는
Codex 자식도 별도로 있었다. 두 조건을 구분하며, 현재 관찰을 과거 스크린샷 시점의
프로세스 상태로 소급하지 않는다.

경로 조회 실패를 무조건 무시하거나 프로세스 이름으로 예외 처리하지 않는다.
메모리 매핑 목록만으로 주 실행 파일의 부재를 증명하는 방식도 사용하지 않는다.

## 수정한 동작

1. 모든 일반 coordinator 실행은 실행 파일 **inode**에 읽기 전용 shared `flock`을 잡는다.
   Pet, 서비스, Hook, MCP뿐 아니라 standalone·심볼릭 링크·이름이 바뀐 번들에서도 유지한다.
2. 검증된 호환 릴리스 교체는 이전 파일에 exclusive 잠금을 잡는다. 사용자가 남아 있으면
   즉시 중단하며 기다리는 설치 때문에 Codex를 종료하거나 승인하지 않는다.
3. 새 복사본에도 exclusive 잠금을 잡아 게시·최종 확인이 끝날 때까지 시작을 막는다.
   이전 파일 잠금은 백업·게시·실패 복구 전체에서 유지된다.
4. 각 경합 지점에서 열린 FD와 현재 파일의 device/inode/크기/수정 시각 등을 다시 비교한다.
   내용이 같은 다른 inode로 바꿔도 검사에 걸린다. 불확실한 복구 자료는 보존한다.
5. 종료 시 FD가 닫히며 잠금은 OS에서 해제된다. `FD_CLOEXEC`을 확인하여 외부 실행 파일에
   잠금이 이어지지 않게 한다. 자식의 `LOCK_UN`으로 부모 잠금을 풀지 않는다.
6. 패키지 실행은 잠금을 잡은 뒤 현재 실행 코드와 디스크의 서명·manifest를 확인한다.
   다른 계정이 설치한 읽기 가능한 앱의 정상 실행은 허용하되, 교체 권한은 완화하지 않는다.

별도 상주 프로세스, 영구 lock 파일, Codex 래퍼 또는 Codex 바이너리 수정은 추가하지 않는다.
두 정확한 읽기 전용 명령 `runtime-use-lease-protocol`, `runtime-identity --app <경로>`는
일반 디스패치 전에 끝나며 런타임 잠금 대상이 아니다. 잘못된 인자는 일반 작업으로 넘기지 않는다.

## 지원 표시만으로 안전 검사를 생략하지 않음

대상 앱의 `BlabeeRuntimeUseLeaseProtocol` 표시만으로는 새 경로를 사용하지 않는다.
현재 실행 중인 검증된 설치 앱과 대상의 runtime identity가 같거나, 설치 앱의 봉인된
`BlabeeRuntimeUseLeasePreviousIdentities`에 **대상의 정확한 identity**가 있어야 한다.

패키징은 다음을 강제한다.

- 새 coordinator가 제한 시간·출력 크기 안에서 정확한 protocol 응답을 내야 조립 가능하다.
- 이전 릴리스는 명시한 `compatiblePreviousApps`에서만 선정한다. 서명 검사, 별도 복사본의
  protocol 응답, 검사 전후 identity/manifest 일치가 필요하다.
- coordinator와 검증된 launcher 외 실행 파일, 심볼릭 링크, 달라진 launcher가 있으면
  실행 잠금 호환 목록에서 제외한다. 기존 전송 호환 정책과는 별개다.
- 승인한 identity 목록은 manifest 작성과 코드 서명 **전에** Info.plist에 봉인한다.

따라서 빌드 번호만 높이거나 구형 실행 파일에 새 plist를 붙이는 것으로 지원이 활성화되지 않는다.
릴리스 제작자는 실제 이전 배포 앱을 호환 입력으로 지정해야 한다. 등록되지 않은 이전 버전은
자동으로 신뢰하지 않고 기존 보호로 돌아간다.

## 현재 구형 설치본에서의 첫 이관

build 18에는 실행 잠금 코드가 없다. 새 설치 프로그램이 이미 실행 중인 구형 프로세스에
잠금을 소급해서 붙일 수 없으므로 **첫 교체에는 기존 전역 검사를 유지한다.**

- `실행 중`: Blabee 또는 연결된 Codex의 Blabee 보조 프로세스가 실제로 확인됐다.
  작업 저장 후 해당 앱·세션을 정상 종료한다.
- `확인 불가`: Blabee 실행의 증거가 아니라 기존 검사 방식의 한계다. 작업 저장 후 Mac을
  재시작하고, Blabee·Codex 등 이전 보조 프로세스를 다시 시작하기 전에 새 앱을 설치한다.
- `실행 잠금 확인 불가`: 새 잠금의 파일/권한/I/O 확인 실패다. 구형 프로세스 조회 실패와
  다른 오류로 표시하며 설치를 중단한다.

자동 재부팅, 다른 앱 강제 종료, 설치 보호 생략, 사용자 데이터·Codex 설정 변경은 하지 않는다.
이 최초 이관을 끝냈다는 실사용 증거 없이는 “현재 설치본 문제가 해결됐다”고 보고하지 않는다.

  Finder/셸 복사로 설치 보호를 우회하지 않았다. 연결된 Codex 세션을 정상 종료한 뒤
  r23 설치창에서 다시 확인해야 한다. 다른 앱 조회 실패가 이어지면 앞의 첫 이관 절차를 따른다.
