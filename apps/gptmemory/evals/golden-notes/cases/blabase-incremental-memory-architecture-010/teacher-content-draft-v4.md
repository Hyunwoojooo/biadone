# Blabase 대화 기억의 관계 판정과 증분형 구조

## 한눈에 보기

- Blabase가 AI 대화를 의미 단위로 자르고 세션 간 관계를 연결하는 방법을 2026년 7월 20일 회의 맥락에서 논의했다.
- 제안의 핵심은 벡터로 후보를 찾고 LLM이 관계를 판정하며, 새 기억 주변만 갱신하고 최종 점수는 조회 시 계산하는 것이다.
- 아키텍처 제안은 4:3 구조도로 만들어졌지만 실제 구현 사양으로 승인되지는 않았다.

## 핵심 정리

- 벡터는 관련 기억의 **후보 검색**, LLM은 관계의 **종류·방향·시간성 판정**, 외부 저장소는 판정 결과의 **지속적 기억**을 맡는 역할 분리가 제안됐다.
- 대화 조각은 고정 토큰이 아니라 결정·작업·문제·선호처럼 독립적으로 이해되는 `Memory Atom`으로 만드는 안이 제시됐다.
- 세션 증가에 대응하는 핵심은 전역 weight 재계산이 아니라 append-only 저장, Top-K 국소 연결, 조회 시점 랭킹과 비동기 통합이다.
- 과거 근거와 현재 상태를 함께 보존하기 위해 계층형 메모리, 시간 관계, Current State Projection과 Sparse Graph가 검토됐다.

## 주제별 정리

### 1. 핵심 병목과 벡터의 한계

사용자가 정의한 병목은 두 가지였다. 하나는 긴 AI 대화를 어떤 의미 단위로 잘라야 하는가이고, 다른 하나는 서로 다른 세션에서 나온 정보를 어떤 관계로 연결해야 한 사람의 맥락을 복원할 수 있는가였다. GPT·Gemini·Kimi 같은 생성 모델의 벡터 공간이 이 문제를 직접 해결할 수 있는지도 질문했다.

생성 모델 내부 상태와 제품이 관리하는 임베딩 인덱스는 구분해야 한다는 설명이 제시됐다. Blabase가 각 모델의 내부 벡터를 공용 메모리처럼 직접 읽는 것이 아니라, 별도 임베딩 모델로 기억을 벡터화해 자체 인덱스에 저장하는 방식이다. 같은 인덱스 안에서는 임베딩 모델과 버전을 고정해야 서로 다른 시점의 벡터를 비교할 수 있다는 조건도 붙었다.

벡터 근접도는 주제나 의미가 비슷한 후보를 빠르게 찾는 데 적합하지만, 두 기억이 왜 연결되는지는 말해주지 않는다. 예를 들어 Cloudflare 비용 결정은 서버 문제의 해결책일 수 있고, 이후의 색상 결정은 이전 결정을 대체할 수 있다. 따라서 후보 검색은 벡터가 맡고, LLM이 `CONTRADICTS`, `SUPERSEDES`, `CAUSES`, `RESOLVES`, `DEPENDS_ON` 같은 제한된 관계의 유형·방향·시간 순서를 판정하는 역할 분리가 제안됐다.

### 2. Memory Atom과 시간적 관계

고정 토큰 청킹은 “그거 괜찮다”처럼 앞 문맥에 의존하는 발화를 독립적인 기억으로 만들기 어렵다. 이를 보완하기 위해 결정·작업·문제·질문·선호·사실·아이디어처럼 의미가 완결된 `Memory Atom`을 추출하고, 지시 대상이 드러나는 독립 문장으로 정규화하는 안이 제시됐다.

Atom에는 내용 외에도 적용 범위인 `scope`, 유효 기간인 `valid_from`·`valid_to`, 사용자가 직접 말한 사실인지 시스템 추론인지 나타내는 `epistemic_status`, 원문 위치와 추출 신뢰도를 함께 두도록 제안됐다. 이는 “Blabase UI에 보라색을 쓰기로 했다”라는 프로젝트 한정 결정을 “사용자는 보라색을 일반적으로 좋아한다”라는 전역 선호로 잘못 확장하는 문제를 줄이기 위한 장치다.

과거 결정을 최신 요약으로 덮어쓰는 대신, 변경 이력을 관계로 남기는 방식도 검토됐다. 새 결정이 이전 결정을 대체하면 `SUPERSEDES`로 연결하고, 현재 유효한 선호·프로젝트·미완료 항목은 그래프에서 계산한 `Current State Projection`으로 제공한다. 이 구조는 과거 근거를 보존하면서도 질의 시점에는 현재 상태를 짧게 제시하기 위한 제안이다.

### 3. 증분형 확장 구조

사용자는 새 세션마다 많은 데이터가 생기는데 기존 모든 기억의 weight를 다시 계산할 수 없다는 확장성 문제를 제기했다. 이에 모델 파라미터나 최종 weight를 사용자 대화마다 갱신하지 않고, `importance`, 관계 신뢰도, 반복·모순 횟수, 최초·최근 관측 시각과 scope 같은 원시 신호를 저장하는 방안이 제시됐다. 최신성 감쇠도 DB에 계속 덮어쓰지 않고 `last_seen_at`을 기준으로 조회 순간 계산한다.

새 Atom이 들어오면 전체 기억과 전수 비교하지 않는다. 사용자·프로젝트·기억 유형·기간으로 후보 범위를 좁힌 뒤 벡터와 키워드 검색으로 Top-K만 가져오고, 그 쌍에 대해서만 LLM 관계 판정을 수행하는 국소 업데이트 방식이다. 최종 랭킹은 질의 유사도, 범위 일치, 최신성, 반복 근거와 모순 패널티를 조회 시 결합하므로 정책이 바뀌어도 전체 데이터를 다시 쓰지 않아도 된다는 설명이다.

기억량을 관리하기 위해 `L0 Raw Conversation → L1 Session Memory → L2 Consolidated Memory → L3 Current State Projection`으로 압축하는 계층도 제안됐다. 최근 미통합 데이터를 담는 Hot/Delta Index와 정리된 장기 기억을 담는 Base Index를 분리하고, 조회 시 양쪽 결과를 합쳐 재정렬하는 방식이다. 실시간 경로에서는 원본 저장·주요 Atom 추출·Hot Index 삽입·명확한 상태 변경만 처리하고, 중복 병합과 장기 압축은 후속 작업으로 넘기는 eventual consistency 접근이다.

관계 그래프는 유사한 모든 기억을 직접 연결하지 않는 Sparse Graph로 유지하는 안이다. 모순·대체·인과·해결·의존 같은 강한 관계만 edge로 저장하고, 단순히 같은 주제인 기억은 Topic Node를 공유하게 해 edge 폭증을 막는다. 이 계층·인덱스·그래프 구성은 설계 후보이며 실제 규모에서 검증된 최종 사양은 아니다.

### 4. 구조도 산출물

앞서 논의한 후보 검색, 관계 판정, 증분 업데이트, 메모리 계층과 조회 흐름을 한 장에 배치한 인포그래픽이 생성됐다. 최초 결과는 세로로 길었고, 사용자가 4:3 비율을 요청해 같은 내용을 가로형으로 재배치한 수정본이 만들어졌다.

사용자가 명시적으로 확정한 것은 구조도를 만들고 비율을 바꾸라는 요청과 그 결과뿐이다. 도식에 포함된 Memory Atom, Hot/Base Index, Sparse Graph, 점수식과 eventual consistency를 Blabase의 최종 기술 사양으로 승인한 것은 아니다.

## 결론과 확정된 결정

- **정리된 결론:** 벡터는 관계 후보 검색, LLM은 유형·방향 판정, 외부 DB·그래프는 결과 보존을 맡는 구조가 적합하다는 제안이다.
- **확정된 요청·결과:** 사용자는 전체 구조도와 4:3 비율 수정을 요청했고 결과에 반영됐다.
- **주의:** Memory Atom·Sparse Graph·Hot/Base 구조의 채택은 확정되지 않았다.
