# Blabase 대화 기억 시스템의 증분형 아키텍처 논의와 4:3 구조도 제작

## 개요

대화는 2026년 7월 20일 Blabase 회의 기록을 바탕으로, 여러 AI 대화 세션을 구조화하고 세션 간 관계를 파악하는 기술 아키텍처 질문에서 시작되었다. 사용자는 GPT·Gemini·Kimi와 같은 대형 모델의 벡터 공간을 활용해 관련 대화를 직접 판별할 수 있는지 물었고, 이후 세션이 누적될 때 모든 weight를 계속 갱신하기 어려운 확장성 문제로 질문을 구체화했다. assistant는 벡터 검색, LLM 관계 판정, 계층형 메모리, 증분 업데이트와 조회 시점 점수 계산을 결합한 구조를 제안했으며, 마지막에는 전체 내용을 도식화한 뒤 사용자 요청에 따라 가로세로 비율을 4:3으로 수정했다.

## 01. 7월 20일 회의 기록과 기술적 병목 제시

사용자는 2026년 7월 20일 20:58 KST에 진행된 회의 기록을 공유했다. 회의에서는 위트 있는 페르소나와 보라색 기반 UI, 직관적인 서비스 용어, Cloudflare 유료 플랜, 3층 아키텍처, 반복 업무의 AI 자동화와 지속적인 배포 방향 등이 논의되었다. 회의 기록상 김동민은 페르소나 구상, UI 레퍼런스 공유, 아키텍처 학습과 UI 정리를 맡고, Hyunwoo Joo는 메인 UI 제작, 용어 정의, Cloudflare 설정 수정과 아키텍처 구현을 맡는 것으로 정리되어 있었다.

이 기록을 배경으로 사용자는 Blabase의 핵심을 “AI와 나눈 대화를 구조화해서 잘라내고, 서로 다른 세션의 대화 간 관계성을 파악해 그 사람의 맥락을 이해하는 것”이라고 설명했다. 현재 병목은 대화를 어떤 단위로 구조화하고, 잘라낸 정보 사이의 상관관계를 어떤 방식으로 연결할지에 있다고 짚었다. 이어 GPT, Gemini, Kimi3 등 기존 대형 모델을 사용할 예정이므로, 모델의 벡터 공간에서 가까운 위치에 있는 정보들을 모델이 직접 판단할 수 있지 않겠느냐고 질문했다.

## 02. 벡터 유사도와 관계 판정의 역할 분리 제안

assistant는 사용자의 생각이 일부는 타당하지만, 벡터 근접도만으로 Blabase가 필요로 하는 관계를 완성할 수는 없다고 답했다. 제안의 핵심은 “벡터는 후보를 찾고, LLM은 관계를 판정하며, 그래프와 데이터베이스가 그 판단을 기억해야 한다”는 역할 분리였다.

assistant는 생성 모델 내부의 벡터와 제품이 외부에서 사용하는 임베딩 벡터를 구분했다. Blabase가 GPT나 Gemini의 내부 상태를 직접 공용 메모리처럼 사용하는 것이 아니라, 별도의 임베딩 모델로 대화 조각을 벡터화하고 이를 자체 벡터 인덱스에 저장해야 한다고 설명했다. 또한 서로 다른 임베딩 모델이나 버전에서 생성된 벡터를 하나의 공간에서 직접 비교해서는 안 되므로, 생성 모델은 교체 가능하게 두더라도 하나의 벡터 인덱스에는 동일한 임베딩 모델과 버전을 사용하는 방식을 제안했다.

## 03. 단순 유사도에서 방향성과 시간성을 가진 관계로 확장

assistant는 벡터 근접도가 두 텍스트의 주제나 의미가 비슷한지를 찾는 데는 유용하지만, 실제 관계의 종류와 방향까지 설명하지는 못한다고 구분했다. 예를 들어 서버 배포 문제와 Cloudflare 유료 플랜 결정은 문제와 해결책 관계이고, 기존 보라색 UI 결정과 이후 다른 색상 결정은 단순 유사성이 아니라 이전 결정을 대체하는 관계일 수 있다고 설명했다.

이 때문에 관계를 `SAME_AS`, `ELABORATES`, `CONTRADICTS`, `SUPERSEDES`, `CAUSES`, `RESOLVES`, `DEPENDS_ON`, `ALTERNATIVE_TO`, `PART_OF`, `ABOUT` 등 제한된 유형으로 판정하는 방식을 제안했다. 벡터 검색은 각 새 기억과 연관 가능성이 높은 후보만 찾고, LLM은 후보 쌍을 대상으로 관계의 종류, 방향, 시간적 선후, 신뢰도와 근거를 구조화된 형태로 반환하는 역할을 맡는 구성이었다. 다만 이 관계 유형과 구체적인 수는 assistant의 설계 제안이며, 사용자가 현재 대화에서 최종 확정한 것은 아니다.

## 04. 대화 분할 단위를 Memory Atom으로 정의하는 방안

assistant는 대화를 일정 토큰 수로 기계적으로 자르는 방식보다, 결정·작업·문제·질문·선호·사실·아이디어처럼 의미가 완결된 `Memory Atom` 단위로 구조화할 것을 제안했다. 대화 속 “그거 괜찮은 것 같다”와 같은 표현은 그대로 저장하면 맥락이 사라지므로, 대상과 의미가 명시된 독립 문장으로 재작성해 저장해야 한다고 설명했다.

각 Memory Atom에는 적용 대상과 범위를 나타내는 `scope`, 유효 기간을 나타내는 `valid_from`과 `valid_to`, 사용자가 명시한 내용인지 시스템 추론인지 구분하는 `epistemic_status`, 원문 위치를 추적하는 `source_span`, 추출 신뢰도 등을 함께 저장하는 방안을 제안했다. 이를 통해 “Blabase UI에 보라색을 쓰기로 했다”는 프로젝트 한정 결정을 “사용자는 일반적으로 보라색을 좋아한다”는 개인 성향으로 과도하게 일반화하는 문제를 줄일 수 있다고 설명했다.

## 05. 3층 아키텍처와 현재 상태 Projection 제안

회의 기록에 포함된 3층 구조를 대화 기억 시스템에 적용하는 방안으로, assistant는 세 계층을 제시했다. 첫 번째는 원본 대화 보존, 화자·시간 기록, 의미 단위 분할과 Memory Atom 추출을 담당하는 `Evidence & Parsing Layer`였다. 두 번째는 Memory, Entity, Topic, 관계 Edge, 벡터 인덱스, 시간 상태와 근거 정보를 보관하는 `Memory & Relationship Layer`였다. 세 번째는 현재 질문에 필요한 기억을 검색하고 그래프를 탐색해 모델 입력용 Context Pack을 만드는 `Context Runtime Layer`였다.

또한 사람에 대한 맥락을 하나의 긴 요약문으로 계속 덮어쓰는 대신, 안정적인 프로필, 현재 선호, 진행 중인 프로젝트, 미완료 항목, 최근 사건과 과거 상태를 분리해 관리하는 방식을 제안했다. 과거 결정은 삭제하지 않고 `SUPERSEDES` 관계로 변경 이력을 남기며, 현재 상태는 그래프 전체에서 계산한 `Current State Projection`으로 제공하는 구성이었다. assistant는 Blabase의 기술적 차별점이 범용 임베딩 모델 자체보다 대화를 의미 단위로 만드는 Memory IR, 시간에 따른 관계를 연결하는 Temporal Linker, 질문별 맥락을 조립하는 Context Compiler에 있을 가능성이 높다고 제안했다.

## 06. 세션 증가에 따른 weight 갱신 문제로 질문 구체화

사용자는 대화 세션마다 데이터가 예상보다 많이 발생하기 때문에, 새 세션을 입력할 때마다 기존 데이터의 weight 값을 계속 업데이트할 수 없다고 문제를 제기하고 대안을 물었다. 이에 assistant는 전체 재계산을 피하는 원칙으로 `Append-only 저장`, `새 데이터 주변만 연결`, `조회 시점 점수 계산`, `주기적 압축`을 제안했다.

assistant는 우선 모델 자체의 파라미터를 사용자 대화마다 업데이트하지 않고, 사용자 기억을 모델 외부에 저장해야 한다고 설명했다. 같은 임베딩 모델과 버전을 유지한다면 기존 대화 벡터도 재계산하지 않고 새 Memory Atom의 벡터만 추가하면 된다고 했다. 시간에 따라 감소하는 recency 값 역시 DB에 계속 덮어쓰지 않고, `last_seen_at` 같은 원시 시각만 저장한 뒤 조회 시점에 감쇠 함수로 계산하는 방식을 제안했다.

## 07. 증분형 메모리, 계층형 압축과 Sparse Graph 설계

assistant는 하나의 최종 weight를 저장하는 대신 `importance`, `relation_confidence`, `support_count`, `contradiction_count`, `first_seen_at`, `last_seen_at`, `scope`, `status`처럼 점수를 구성하는 신호를 저장하고, 실제 질문이 들어왔을 때 `query_similarity`, 범위 일치, 최신성, 반복 근거와 모순 패널티를 조합해 최종 점수를 계산할 것을 제안했다. 점수 공식이나 가중치 정책이 바뀌어도 전체 기억을 다시 갱신하지 않고 랭킹 정책 버전만 교체할 수 있다는 설명이었다.

새 세션 처리 시에는 전체 기억과 비교하지 않고, 새 세션에서 추출한 Atom별로 사용자·프로젝트·기억 유형·기간 등의 범위를 먼저 제한한 뒤 벡터 검색과 키워드 검색을 결합해 Top-K 후보만 찾고, 그 후보에 대해서만 LLM 관계 판정을 수행하는 방식을 제안했다. 새 데이터가 영향을 미친 소수의 Edge와 Current State key만 수정하고 다른 기억은 유지하는 증분형 구조였다.

데이터 규모를 줄이기 위해 메모리를 `L0 Raw Conversation`, `L1 Session Memory`, `L2 Consolidated Memory`, `L3 Current State Projection`의 네 단계로 관리하는 방안도 제시됐다. 원본은 보존하되 모든 문장을 장기 기억으로 올리지 않고, 여러 세션에 반복되는 기억은 대표 기억으로 통합하면서 원본 근거는 연결해 두는 구조였다. 최근에 들어와 아직 통합되지 않은 데이터를 담는 `Hot/Delta Index`와 정리된 장기 기억을 담는 `Consolidated/Base Index`를 분리하고, 조회 시 두 인덱스의 결과를 합쳐 재정렬하는 방식도 제안했다.

관계 그래프는 모든 유사 기억을 서로 연결하지 않는 `Sparse Graph`로 유지하도록 제안했다. 모순, 대체, 인과, 해결, 의존처럼 강한 관계만 직접 Edge로 저장하고, 단순히 같은 주제인 기억은 공통 Topic Node를 통해 묶는 방식이었다. 실시간 입력 과정에서는 원본 저장, 주요 Atom 추출, 새 Atom 임베딩과 Hot Index 삽입, 명확한 상태 변경 반영까지만 수행하고, 중복 병합과 장기 압축은 별도 통합 과정에서 처리하는 eventual consistency 구조가 적합하다고 설명했다.

## 08. 전체 구조도 생성과 4:3 비율 수정

사용자는 앞서 논의한 전체 내용을 도식화해 달라고 요청했다. assistant는 Blabase 대화 기억 아키텍처를 한눈에 볼 수 있도록 핵심 원칙, 세션 입력 흐름, 메모리 계층, 조회 시 점수 계산, Edge 저장, Hot/Base 인덱스, Sparse Graph, 데이터 모델과 즉시·후속 처리 경로를 포함한 인포그래픽을 생성했다.

처음 생성된 구조도는 세로로 긴 형태였고, 사용자는 가로세로 비율을 4:3으로 설정해 달라고 수정 요청했다. assistant는 같은 전체 내용을 가로형 4:3 구성으로 다시 배치한 구조도를 생성했다. 이 비율 변경은 사용자가 명시적으로 요청하고 결과에 반영된 최종 수정 사항이다.

## 현재 도달한 상태

대화 마지막 시점에는 Blabase의 대화 기억 시스템을 전체 weight 재계산 방식이 아니라, 새 기억만 추가하고 관련 후보만 국소적으로 연결하며 점수는 조회 시 계산하는 증분형 구조로 설명한 상태에 도달했다. 계층형 메모리, Hot/Base 인덱스, Sparse Graph, Current State Projection 등은 assistant가 제안한 기술 설계이며, 현재 대화에서 사용자가 개별 구성 요소를 최종 구현안으로 확정한 기록은 없다. 논의된 전체 구조는 인포그래픽으로 도식화되었고, 마지막 사용자 요구에 따라 4:3 비율로 수정된 결과가 생성되었다.

## 주요 수정 및 방향 전환

* 모델의 벡터 근접도만으로 관계 연결 → 벡터는 후보 검색에 사용하고 LLM이 관계 유형·방향·시간성을 판정하는 구조
* 모든 세션 입력 시 기존 weight 전역 업데이트 → 새 Atom과 관련된 소수의 기억만 국소 업데이트하고 최종 점수는 조회 시 계산
* 모든 대화 조각을 동일한 장기 기억으로 저장 → Raw Conversation, Session Memory, Consolidated Memory, Current State Projection으로 계층화
* 유사한 기억을 모두 직접 연결 → 강한 관계만 직접 연결하고 일반적인 주제 관계는 Topic Node로 묶는 Sparse Graph
* 최초 세로형 전체 구조도 → 사용자 요청에 따른 4:3 가로형 구조도

## 구분해서 표현해야 할 내용

* **assistant가 제안했지만 사용자가 확정하지 않은 내용:** Memory Atom 스키마, 관계 유형 목록, 3층 기억 처리 구조의 구체적 구성, 4단계 메모리 계층, Hot/Delta와 Base Index 분리, Sparse Graph, 조회 시점 점수 공식, eventual consistency 처리 방식, 관계형 DB 테이블 구성.
* **사용자가 명시적으로 선택하거나 확정한 내용:** 회의 기록상 보라색 기반 UI, 직관적 용어, Cloudflare 유료 플랜과 3층 아키텍처가 결정된 것으로 제시되었다. 현재 대화에서는 전체 내용을 도식화하는 것과 구조도의 가로세로 비율을 4:3으로 바꾸는 것을 명시적으로 요청했다.
* **아직 해결되지 않은 내용:** assistant가 제안한 여러 기술 구성 중 무엇을 실제 Blabase 구현안으로 채택할지, 임베딩 모델·저장소·후보 수·점수 가중치 등을 어떤 값으로 확정할지는 대화에서 결정되지 않았다.

## 요약에서 주장하면 안 되는 내용

* Blabase가 제안된 Memory Atom·Sparse Graph·Hot/Base Index 구조를 이미 구현했다는 주장.
* 사용자가 assistant의 전체 아키텍처 제안을 최종 기술 사양으로 승인했다는 주장.
* GPT, Gemini, Kimi의 내부 벡터를 Blabase가 직접 접근하거나 공유할 수 있다는 주장.
* 제시된 Top-K 수, 점수 가중치, 메모리 계층별 Atom 수가 실험으로 검증된 최적값이라는 주장.
* 4:3 구조도가 실제 제품 아키텍처의 최종 확정 문서라는 주장.
