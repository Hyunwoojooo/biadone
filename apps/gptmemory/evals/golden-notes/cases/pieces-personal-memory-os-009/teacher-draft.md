# Pieces OS와 유사한 로컬 퍼스널 메모리 시스템의 단계별 구현 구상

## 개요

대화는 사용자가 Pieces OS와 같은 제품을 만들려면 어떤 방식으로 접근해야 하는지 단계별 설명을 요청하면서 시작되었다. 이에 assistant는 Pieces의 외형이나 고유 요소를 그대로 복제하기보다는, 사용자 활동을 수집하고 기억으로 가공한 뒤 타임라인과 대화형 검색으로 다시 활용하는 **기능적 등가의 local-first Personal Memory OS**로 구현해야 한다고 제안했다. 이후 초기 MVP 범위부터 로컬 데몬, 데이터 모델, 검색, 프라이버시, 확장 통합, 장기 개발 로드맵까지 순차적으로 설명했다.

## 01. Pieces OS 복제가 아닌 기능 구조 재현으로의 재정의

사용자는 “Pieces OS를 똑같이 만들려면” 어떻게 해야 하는지 step by step으로 설명해 달라고 요청했다. Assistant는 상표, UI, 코드, 고유 표현을 직접 복제하는 방식은 피하고, Pieces와 같은 역할을 수행하는 제품을 만드는 방향으로 요청을 재해석했다. 그 핵심 구조를 **사용자 활동 캡처 → 로컬 이벤트 저장 → 요약·태깅·임베딩·민감정보 필터링 → 장기기억 저장 → 타임라인 → 대화형 검색 → IDE·브라우저·데스크톱 호출**의 흐름으로 제시했다.

이 재정의는 assistant의 제안이었으며, 사용자가 별도로 동의하거나 확정한 내용은 대화 안에서 확인되지 않았다.

## 02. 초기 MVP 범위와 로컬 백엔드 구조 제안

Assistant는 처음부터 전체 화면, 모든 앱, 시스템 오디오까지 수집하지 말고, 브라우저 탭과 선택 텍스트, VS Code 또는 JetBrains의 프로젝트·파일 정보, 클립보드, 지정 폴더의 문서, 사용자가 직접 저장한 스니펫과 메모부터 다루는 것이 적절하다고 제안했다. 화면 캡처, 오디오, 전면적인 OS 접근은 권한·프라이버시·성능 문제가 크므로 후순위로 배치했다.

제품의 기반으로는 항상 실행되는 로컬 백엔드 데몬을 두고, 데스크톱 앱은 Tauri와 React, 로컬 서비스는 초기에는 FastAPI 또는 이후 Rust Axum, 저장소는 SQLite·FTS5와 벡터 저장소, 파일 원본은 로컬 파일 시스템에 보관하는 구성을 제시했다. `/capture`, `/timeline`, `/search`, `/chat`, `/summarize`, 프라이버시 설정과 기억 삭제 API가 최소 인터페이스로 제안되었다.

## 03. 원본 이벤트와 정제된 기억을 분리하는 데이터 설계

Assistant는 Pieces류 제품을 단순한 대화 기록 저장소가 아니라 시간 기반 활동 기억 저장소로 보아야 한다고 설명했다. 이에 따라 사용자의 실제 활동을 담는 `raw_events`, AI가 정리한 의미 단위인 `memory_items`, 일정 시간 동안의 작업을 묶는 `timeline_blocks`를 분리하는 데이터 모델을 제안했다.

원본 이벤트에는 앱, URL, 파일 경로, 프로젝트 경로, 원문 텍스트, 시간, 권한 범위 등을 저장하고, 정제된 기억에는 요약, 엔티티, 태그, 임베딩, 중요도, 신뢰도, 유효 기간 등을 저장하도록 했다. 이러한 분리는 사용자가 특정 기억을 수정하거나 앱·기간별 데이터를 삭제해야 할 때 필요하다는 설명이 뒤따랐다.

## 04. 캡처 어댑터와 기억 형성 파이프라인

데이터 수집 기능은 하나의 거대한 수집기로 만들지 않고, 브라우저 확장 프로그램, VS Code 확장 프로그램, 클립보드 감시기, 지정 폴더 감시기, 수동 저장 기능을 각각 독립된 어댑터로 구현하는 방식이 제안되었다.

수집한 데이터를 그대로 벡터 데이터베이스에 넣지 않고, 정규화, 중복 제거, 비밀정보·개인정보 탐지, 청킹, 요약, 엔티티 추출, 시간·앱·프로젝트 태깅, 임베딩, 중요도 평가를 거쳐 기억으로 변환해야 한다고 설명했다. Assistant는 원문 기록과 그로부터 생성한 의미 중심 기억을 구분함으로써, 단순한 활동 로그가 아니라 다시 활용할 수 있는 장기기억을 만들어야 한다고 보았다.

## 05. 하이브리드 검색, 대화형 회상, 타임라인 UX

Assistant는 “어제 보던 문서”, “지난주 조사한 자료”, “아까 복사한 코드”처럼 시간과 맥락이 섞인 질문에는 벡터 검색만으로 부족하다고 설명했다. 따라서 정확한 명칭을 찾는 키워드 검색, 의미 기반 벡터 검색, 시간·앱·프로젝트 필터, 재정렬, 근거가 부족할 때 답변을 제한하는 신뢰도 판단을 결합한 하이브리드 검색 구조를 제안했다.

대화형 검색에서는 전체 기억, 오늘, 어제, 최근 7일, 특정 앱, 프로젝트, 폴더, 브라우저 또는 IDE 활동 등 검색 범위를 선택할 수 있도록 하고, 답변에는 어떤 시간에 어떤 앱·파일·URL에서 확인된 내용인지 근거를 붙여야 한다고 했다. 타임라인은 시간대별 작업 세션을 요약해서 보여주고, 각 블록에서 관련 앱, URL, 파일, 대화, 태그, 질문하기, 삭제, 기억 고정 기능으로 진입하는 중심 화면으로 제안되었다.

## 06. 모델 라우팅과 프라이버시 우선 설계

Assistant는 민감한 기억 검색과 요약에는 로컬 LLM을 우선 사용하고, 긴 보고서 작성이나 비민감 작업은 사용자가 허용한 경우 클라우드 모델을 선택할 수 있도록 하는 로컬·클라우드 모델 라우터를 제안했다. Ollama, LM Studio, OpenAI, Anthropic, Google 등을 하나의 모델 게이트웨이로 추상화하는 구상도 포함되었다.

프라이버시는 부가 기능이 아니라 제품의 우선 요구사항으로 다뤄졌다. 앱별 캡처 허용·차단, 은행·병원·비밀번호 관리자 등 민감 앱의 사전 차단, 기간·앱·수집 방식별 삭제, 로컬 암호화, 클라우드 전송 전 명시적 동의, 텔레메트리 제어 등이 필수 기능으로 제안되었다. 화면 캡처와 오디오는 수동 저장과 브라우저·IDE·클립보드 수집이 안정화된 이후 단계적으로 추가하는 순서가 제시되었다.

## 07. 개발자 자산, 외부 통합, 기억 계층 확장

Pieces의 개발자 도구 성격을 재현하기 위해 코드 스니펫, 프롬프트, 문서 조각, URL, 이미지, PDF, 회의 요약, 의사결정, 아이디어를 재사용 가능한 자산으로 별도 관리하는 기능이 제안되었다. 접근 채널은 Chrome 확장, VS Code 확장, 글로벌 단축키, Raycast·Alfred, MCP 서버, JetBrains 플러그인, Slack·Notion·Gmail 등의 순서로 확장하도록 했다.

기억은 최근 작업을 다루는 단기기억, 오늘부터 최근 수주까지의 프로젝트 흐름을 다루는 중기기억, 반복되는 선호·장기 프로젝트·관계·의사결정 이력·습관을 다루는 장기 개인기억으로 나누는 구조가 제안되었다. Assistant는 장기적으로 단순한 Pieces 유사 제품을 넘어 사용자의 습관과 반복 문제를 감지하고 필요한 행동을 먼저 제안하는 형태로 확장할 수 있다고 설명했다.

## 08. 단계별 개발 로드맵과 최종 구현 순서

Assistant는 개발을 네 단계 이상으로 나눴다. 초기 단계에서는 로컬 데몬, SQLite·FTS5, 브라우저와 VS Code 확장, 클립보드, 수동 저장, 기본 검색과 간단한 채팅형 RAG를 구현하도록 했다. 다음 단계에서는 타임라인, 작업 세션 요약, 벡터·키워드 결합 검색, 시간·앱·프로젝트 필터, 답변 근거, 삭제 UI와 앱 허용·차단을 추가하는 흐름이었다.

그 이후 로컬 모델, 클라우드 모델 선택, 프로젝트 기반 대화, 일일 요약과 스탠드업 기능을 붙이고, 장기적으로 화면 OCR, 오디오 전사, MCP, JetBrains, 암호화 동기화, 기억 그래프, 기억 충돌 처리까지 확장하는 계획을 제시했다. 마지막에는 가장 현실적인 구현 순서를 로컬 데몬부터 시작해 저장소, 브라우저, IDE, 클립보드, 검색, 기억 처리, 하이브리드 검색, 채팅, 타임라인, 프라이버시, 로컬 모델, MCP, 화면 OCR, 오디오, 선제 제안 순으로 정리했다.

## 현재 도달한 상태

대화 마지막 시점에는 Pieces OS와 유사한 제품을 구현하기 위한 상세한 기술·제품 로드맵이 assistant의 제안으로 정리된 상태다. 초기 제품은 브라우저, VS Code, 클립보드에서 활동을 수집하고 로컬에서 검색·회상할 수 있는 시스템으로 좁히며, 이후 타임라인, 로컬 AI, 화면·오디오, 장기기억과 선제 제안으로 확장하는 방향이 제시되었다. 다만 사용자는 이 가운데 특정 기술 스택, MVP 범위, 개발 순서 또는 장기 확장 방향을 명시적으로 선택하거나 확정하지 않았다.

## 반드시 포함해야 할 맥락

* 사용자는 Pieces OS와 같은 제품을 만드는 방법을 단계별로 설명해 달라고 요청했다.
* Assistant는 직접적인 상표·UI·코드 복제 대신 기능적 등가의 local-first Personal Memory OS를 만들자고 제안했다.
* 제안된 전체 구조는 사용자 활동 캡처, 로컬 저장, 기억 가공, 장기기억, 타임라인, 대화형 검색, 외부 도구 호출로 이어졌다.
* 초기 MVP 수집 대상은 브라우저, IDE, 클립보드, 지정 폴더 문서, 수동 저장으로 제한되었다.
* 원본 활동 이벤트와 AI가 정제한 기억, 시간대별 작업 블록을 분리하는 데이터 모델이 제안되었다.
* 검색은 키워드, 벡터, 시간, 앱, 프로젝트 필터와 재정렬을 결합하는 하이브리드 방식으로 설명되었다.
* 프라이버시 제어와 데이터 삭제, 로컬 처리, 앱별 캡처 차단이 핵심 요구사항으로 제안되었다.
* 로컬 데몬과 기본 검색 MVP에서 시작해 타임라인, 로컬 LLM, MCP, 화면 OCR, 오디오, 장기기억과 선제 제안으로 확장하는 로드맵이 제시되었다.

## 주요 수정 및 방향 전환

* 사용자 측의 명확한 수정 또는 철회는 없음.
* Assistant의 재구성: `Pieces OS를 똑같이 구현 → 상표·UI·코드를 복제하지 않고 핵심 기능을 재현하는 local-first Personal Memory OS로 구현`
* 이 변경 방향은 assistant의 제안이며 사용자가 확정한 내용은 아니다.

## 구분해서 표현해야 할 내용

* **Assistant가 제안했지만 사용자가 확정하지 않은 내용:** 기능적 등가 제품으로의 재정의, Tauri·React·FastAPI·Rust·SQLite 등의 기술 구성, 브라우저·VS Code·클립보드 중심 MVP, 하이브리드 검색, 로컬·클라우드 LLM 라우팅, 기억 계층, 단계별 개발 일정과 장기 확장 방향.
* **사용자가 명시적으로 선택하거나 확정한 내용:** Pieces OS와 같은 제품을 만들기 위한 단계별 설명을 요청했다는 사실 외에는 없음.
* **아직 해결되지 않은 내용:** 실제로 어느 범위까지 구현할지, 어떤 기술 스택을 채택할지, Pieces와 유사한 개발자 도구에 집중할지 더 넓은 개인 비서로 확장할지, 실제 개발에 착수할지 여부.
* 사용자가 assistant의 제안 중 특정 항목을 승인했다는 기록은 없음.

## 요약에서 주장하면 안 되는 내용

* 사용자가 assistant가 제안한 기술 스택을 최종 채택했다는 주장.
* 사용자가 4주 또는 특정 기간 안에 MVP를 만들기로 결정했다는 주장.
* 제품명이 정해졌거나 Pieces의 대체재로 출시하기로 확정했다는 주장.
* 사용자가 화면 캡처, 오디오, MCP, 장기 개인기억 기능을 구현하기로 승인했다는 주장.
* 제안된 성능 기준이나 개발 단계가 실제 테스트를 통해 검증되었다는 주장.
