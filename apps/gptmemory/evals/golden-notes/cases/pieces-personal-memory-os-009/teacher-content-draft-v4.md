# Local-first Personal Memory OS 구현 구상

## 한눈에 보기

- Pieces OS와 같은 역할을 하는 제품을 단계적으로 구현하는 방법을 설명한 대화다.
- Assistant는 직접 복제 대신 활동 캡처, 기억 가공, 타임라인과 대화형 검색을 잇는 local-first Personal Memory OS를 제안했다.
- MVP부터 장기 로드맵까지 상세안은 마련됐지만 사용자가 기술 스택이나 구현 범위를 채택하거나 개발에 착수한 것은 아니다.

## 핵심 정리

- 전체 흐름은 `활동 캡처 → 로컬 이벤트 저장 → 정제·요약·태깅·임베딩 → 장기기억 → 타임라인·검색 → 외부 호출`이다.
- 초기 수집은 브라우저, IDE, 클립보드, 지정 폴더와 수동 저장으로 제한하고 화면·오디오는 후순위로 두는 안이다.
- 원본 `raw_events`, 정제된 `memory_items`, 시간대별 `timeline_blocks`를 분리해 삭제·수정과 출처 추적을 가능하게 한다.
- 회상은 키워드·벡터·시간·앱·프로젝트 필터와 재정렬·출처 근거를 결합하는 하이브리드 검색으로 설계하는 안이다.
- 프라이버시 제어를 기반으로 좁은 로컬 MVP에서 타임라인·LLM·화면·오디오·장기기억으로 확장하는 로드맵이 제안됐다.

## 주제별 정리

### 1. 제품의 기능적 재정의

사용자는 Pieces OS와 같은 제품을 단계별로 어떻게 만들 수 있는지 물었다. Assistant는 상표, 화면 구성, 코드와 고유 표현을 그대로 복제하지 않고, Pieces가 수행하는 역할을 기능적으로 재현하는 local-first Personal Memory OS로 요청을 재해석했다. 이 방향은 법적·제품적 위험을 줄이기 위한 제안이며 사용자가 최종 제품 정의로 승인한 것은 아니다.

기능 흐름은 브라우저·IDE·클립보드 등에서 활동을 캡처하고, 원본 이벤트를 로컬에 저장한 뒤 요약·태깅·임베딩·민감정보 필터링을 거쳐 재사용 가능한 기억으로 만드는 것이다. 사용자는 타임라인이나 대화형 검색으로 과거 작업을 회상하고, IDE·브라우저·데스크톱 단축키 같은 여러 접점에서 다시 호출한다. 단순한 대화 기록 보관소보다 시간 기반 활동 기억 시스템으로 보는 관점이 제시됐다.

### 2. MVP와 데이터 파이프라인

초기 MVP에서는 전체 화면, 모든 앱과 시스템 오디오를 한꺼번에 수집하지 않는 안이 제시됐다. 브라우저 탭·선택 텍스트, VS Code나 JetBrains의 프로젝트·파일 정보, 클립보드, 지정 폴더 문서, 사용자가 직접 저장한 스니펫·메모부터 시작한다. 화면·오디오는 권한, 프라이버시와 성능 부담이 크므로 앞 단계가 안정된 뒤 추가하는 순서다.

항상 실행되는 로컬 데몬을 중심에 두고 브라우저 확장, IDE 확장, 클립보드 감시기, 폴더 감시기와 수동 저장을 독립 어댑터로 구성하는 안이 제안됐다. 데스크톱에는 Tauri·React, 초기 로컬 서비스에는 FastAPI 또는 이후 Rust Axum, 저장에는 SQLite·FTS5·벡터 저장소, 파일 원본에는 로컬 파일 시스템을 쓰는 후보가 제시됐다. `/capture`, `/timeline`, `/search`, `/chat`, `/summarize`, 프라이버시 설정과 삭제 API가 최소 인터페이스로 언급됐지만 기술 선택은 확정되지 않았다.

데이터 모델은 실제 활동을 담는 `raw_events`, AI가 정제한 의미 단위인 `memory_items`, 일정 시간의 작업을 묶는 `timeline_blocks`를 분리한다. 원본에는 앱·URL·파일·프로젝트·시간·권한 범위를, 기억에는 요약·엔티티·태그·임베딩·중요도·신뢰도·유효 기간을 보관하는 안이다. 이 분리는 사용자가 특정 기억을 수정하거나 앱·기간별 데이터를 삭제하고, AI 요약을 원문과 다시 대조할 수 있게 하기 위한 제안이다.

수집 데이터는 바로 벡터 DB에 넣지 않고 정규화, 중복 제거, 비밀정보·개인정보 탐지, 청킹, 요약, 엔티티 추출, 시간·앱·프로젝트 태깅, 임베딩과 중요도 평가를 거친다. 원문 활동과 의미 중심 기억을 구분해야 단순 로그가 아니라 다시 활용할 수 있는 장기기억이 된다는 논리다.

### 3. 검색·타임라인과 프라이버시

“어제 보던 문서”, “지난주 조사한 자료”, “아까 복사한 코드”처럼 시간·맥락·정확한 명칭이 섞인 질문에는 벡터 유사도만으로 부족하다는 설명이 제시됐다. 정확한 이름을 찾는 키워드 검색, 의미 기반 벡터 검색, 시간·앱·프로젝트 필터와 재정렬을 결합하고, 근거가 약하면 답변을 제한하는 신뢰도 판단도 포함하는 안이다.

대화형 회상에서는 전체, 오늘·어제·최근 7일, 특정 앱·프로젝트·폴더, 브라우저·IDE 활동처럼 범위를 선택하고, 답변에 시간·앱·파일·URL 근거를 붙인다. 타임라인은 시간대별 작업 세션을 요약해 관련 앱·URL·파일·대화·태그로 들어가고 질문·삭제·고정 작업을 수행하는 중심 화면으로 제안됐다.

프라이버시는 부가 기능이 아니라 제품의 선행 요구사항으로 다뤄졌다. 앱별 캡처 허용·차단, 은행·병원·비밀번호 관리자 같은 민감 앱의 사전 차단, 기간·앱·수집 방식별 삭제, 로컬 암호화, 클라우드 전송 전 명시적 동의와 텔레메트리 제어가 포함됐다. 민감한 기억의 검색·요약은 로컬 LLM을 우선하고, 긴 비민감 작업은 사용자 허용 시 클라우드 모델로 보내는 모델 라우터도 제안됐다.

### 4. 확장 로드맵

개발자 자산으로 코드 스니펫, 프롬프트, 문서 조각, URL, 이미지, PDF, 회의 요약, 의사결정과 아이디어를 별도 관리하는 기능이 제안됐다. 접근 채널은 Chrome·VS Code 확장과 글로벌 단축키에서 Raycast·Alfred, MCP, JetBrains, Slack·Notion·Gmail 순으로 넓히는 안이다.

기억은 최근 작업의 단기기억, 오늘부터 최근 수주의 프로젝트 흐름을 담는 중기기억, 반복 선호·장기 프로젝트·관계·의사결정·습관을 다루는 장기기억으로 구분됐다. 장기적으로는 사용자의 반복 문제와 습관을 감지해 필요한 행동을 먼저 제안하는 방향까지 설명됐으나, 사용자가 이 범위를 승인한 것은 아니다.

구현 순서는 로컬 데몬과 저장소, 브라우저·IDE·클립보드 캡처, 기본 검색과 채팅형 RAG에서 시작해 타임라인·작업 세션 요약·하이브리드 검색·근거·삭제 UI로 확장하는 흐름이다. 이후 로컬·클라우드 모델 선택과 프로젝트 대화·일일 요약을 붙이고, 화면 OCR·오디오·MCP·암호화 동기화·기억 그래프·충돌 처리·선제 제안을 후순위로 두는 로드맵이 제시됐다. 이 순서와 일정은 모두 구현 제안이다.

## 결론과 확정된 결정

- **정리된 제안:** 처음부터 모든 OS 활동을 수집하기보다 local-first의 좁은 MVP에서 시작해 단계적으로 확장한다.
- **사용자 확정 결정:** Pieces OS 같은 제품의 구현법을 요청했다는 사실 외에는 없다.
